DLL Injection Techniques — How They Work

DLL injection is the practice of loading a Dynamic Link Library into the address space of a process that did not explicitly request it. Understanding how these mechanisms work is essential for security researchers, anti-cheat engineers, debugging tool developers, and anyone building software that interacts with running processes — from screen readers to in-game overlays.

What Is DLL Injection?

When Windows loads a DLL normally, the target process calls LoadLibrary("mylib.dll") itself — it is an explicit, consensual load. DLL injection means a second process causes the DLL to appear in the first process's address space without a direct LoadLibrary call in the target binary. Once loaded, the injected DLL's code runs inside the target process with the same privileges and memory access as the target itself.

From a memory layout perspective, injecting a DLL is equivalent to the target process loading it voluntarily: the PE file is mapped into a region of the target's virtual address space, imports are resolved, relocations are applied, and DllMain is called with DLL_PROCESS_ATTACH. The DLL's code can then read and write any memory the process owns, call any function in any loaded module, and create threads that execute indefinitely.

  • Overlays: Steam, Discord, GeForce Experience all inject DLLs to render UI on top of the game's DirectX/Vulkan swap chain.
  • Debugging & profiling: Tools like Intel VTune and RenderDoc inject to intercept graphics API calls.
  • Accessibility: Screen readers inject into browsers to read DOM content that Win32 accessibility APIs cannot reach.
  • Game modding: Script extenders (Skyrim Script Extender, etc.) inject to add new scripting capabilities to games.
  • Security research: Studying how anti-cheat software works, building defenses, and understanding attack surfaces.

LoadLibrary Injection — The Classic Technique

The most widely understood injection method uses CreateRemoteThread to execute LoadLibraryA (or LoadLibraryW) inside the target process. The key insight is that kernel32.dll is loaded at the same base address in every user-mode process on a given Windows session (thanks to ASLR being module-level, not per-process for system DLLs in most configurations). This means the address of LoadLibraryA you read from your own process is valid in the target process too.

Step-by-step walkthrough:

  1. Open the target process with sufficient access rights (PROCESS_ALL_ACCESS or at minimum PROCESS_VM_WRITE | PROCESS_VM_OPERATION | PROCESS_CREATE_THREAD).
  2. Allocate memory in the target for the DLL path string using VirtualAllocEx. The path must be the absolute filesystem path to the DLL you want loaded.
  3. Write the DLL path into the allocated region with WriteProcessMemory.
  4. Resolve LoadLibraryA in your own process via GetProcAddress(GetModuleHandleA("kernel32.dll"), "LoadLibraryA").
  5. Create a remote thread with CreateRemoteThread, setting the thread start address to LoadLibraryA and the parameter to the remote memory pointer holding the DLL path. Windows will call LoadLibraryA(remotePath) in the context of the target process.
  6. Wait and clean up: WaitForSingleObject on the thread handle, then VirtualFreeEx the allocated path memory.
// LoadLibrary injection
// Requires: target process PID, absolute path to DLL
bool InjectDLL(DWORD targetPid, const char* dllPath)
{
    // Step 1: open target process
    HANDLE hProc = OpenProcess(
        PROCESS_VM_WRITE | PROCESS_VM_OPERATION | PROCESS_CREATE_THREAD,
        FALSE, targetPid);
    if (!hProc) return false;

    size_t pathLen = strlen(dllPath) + 1;

    // Step 2: allocate space for the path string inside the target
    LPVOID remoteMem = VirtualAllocEx(
        hProc, nullptr, pathLen,
        MEM_COMMIT | MEM_RESERVE, PAGE_READWRITE);
    if (!remoteMem) { CloseHandle(hProc); return false; }

    // Step 3: write the DLL path into that remote allocation
    if (!WriteProcessMemory(hProc, remoteMem, dllPath, pathLen, nullptr)) {
        VirtualFreeEx(hProc, remoteMem, 0, MEM_RELEASE);
        CloseHandle(hProc);
        return false;
    }

    // Step 4: resolve LoadLibraryA — same address in every process
    FARPROC loadLib = GetProcAddress(
        GetModuleHandleA("kernel32.dll"), "LoadLibraryA");

    // Step 5: create a remote thread that calls LoadLibraryA(remoteMem)
    HANDLE hThread = CreateRemoteThread(
        hProc, nullptr, 0,
        reinterpret_cast<LPTHREAD_START_ROUTINE>(loadLib),
        remoteMem, 0, nullptr);

    if (!hThread) {
        VirtualFreeEx(hProc, remoteMem, 0, MEM_RELEASE);
        CloseHandle(hProc);
        return false;
    }

    // Step 6: wait for LoadLibraryA to complete, then clean up
    WaitForSingleObject(hThread, INFINITE);
    VirtualFreeEx(hProc, remoteMem, 0, MEM_RELEASE);
    CloseHandle(hThread);
    CloseHandle(hProc);
    return true;
}

When LoadLibraryA runs in the target, Windows performs all standard DLL loading: maps the PE, resolves its imports from the target's loaded modules, applies base relocations if needed, and calls DllMain(hModule, DLL_PROCESS_ATTACH, NULL). From that point, the DLL is a permanent resident of the target's memory and appears in the target's module list (queryable via EnumProcessModules).

Manual Mapping — Injecting Without LoadLibrary

Manual mapping bypasses the Windows loader entirely. Instead of asking the OS to load the DLL, the injector replicates what the loader does manually — reading the PE file, mapping its sections into the target, resolving imports, and applying relocations — all from outside the target process. The DLL never appears in the target's module list because LdrLoadDll was never called.

The manual mapping process involves these stages:

  1. Read the PE file into a local buffer. Parse the DOS header → NT headers → Optional header to find SizeOfImage, ImageBase, and the section table.
  2. Allocate a region of SizeOfImage bytes in the target process at any address (pass nullptr to let the OS choose, or attempt the preferred ImageBase).
  3. Copy each PE section (.text, .rdata, .data, etc.) from the raw file buffer to its correct virtual address in the target using WriteProcessMemory, respecting each section's VirtualAddress and SizeOfRawData.
  4. Apply relocations (the base relocation directory — IMAGE_DIRECTORY_ENTRY_BASERELOC) if the image was not loaded at its preferred base. Each relocation entry patches an absolute address in the image.
  5. Resolve imports (the import directory — IMAGE_DIRECTORY_ENTRY_IMPORT). For each imported DLL, find it in the target's loaded modules, resolve each function's address, and write it into the target's Import Address Table (IAT).
  6. Set memory protections — mark .text as PAGE_EXECUTE_READ, .rdata as PAGE_READONLY, etc., using VirtualProtectEx.
  7. Call DllMain via a small shellcode or remote thread, passing the correct hModule, DLL_PROCESS_ATTACH, and NULL arguments.
Note:Manual mapping reveals exactly what the Windows PE loader does internally — the same process occurs for every EXE and DLL Windows loads normally. Understanding manual mapping is equivalent to understanding the Windows loader architecture.

SetWindowsHookEx Injection — Riding the Message Loop

Windows has provided SetWindowsHookEx since Win16 as a legitimate API for intercepting system-wide events — keyboard input, mouse events, window messages. When you install a global hook that processes messages from a DLL (rather than an in-process callback), Windows automatically loads that DLL into every process that receives the hooked message type.

// hook_injector.cpp — conceptual overview
// The DLL to inject must export the hook procedure.

// In the injector process:
HMODULE hHookDll = LoadLibraryA("hook_payload.dll");
HOOKPROC hookProc = (HOOKPROC)GetProcAddress(hHookDll, "GetMsgProc");

// WH_GETMESSAGE fires whenever a thread calls GetMessage() or PeekMessage()
// Setting threadId=0 makes it GLOBAL — hits every GUI thread on the desktop
HHOOK hHook = SetWindowsHookEx(WH_GETMESSAGE, hookProc, hHookDll, 0);

// The first time any GUI thread in any process calls GetMessage(),
// Windows loads hook_payload.dll into that process and calls GetMsgProc.
// After the hook fires once, the DLL is resident. Call UnhookWindowsHookEx
// to remove the hook (but the DLL stays loaded until the process exits).

// ── Inside hook_payload.dll ──────────────────────────────────────────────
LRESULT CALLBACK GetMsgProc(int nCode, WPARAM wParam, LPARAM lParam)
{
    static bool initialized = false;
    if (!initialized) {
        initialized = true;
        // This code runs in the target process context on first message
        CreateThread(nullptr, 0, WorkerThread, nullptr, 0, nullptr);
    }
    return CallNextHookEx(nullptr, nCode, wParam, lParam);
}

This technique does not require OpenProcess or any direct process manipulation — it uses a documented, legitimate Windows API. The injected code runs on the target's own GUI thread (in the hook callback), then typically spawns a worker thread to avoid blocking message processing. Antivirus software flags global hooks from unknown publishers because they are a standard persistence and injection vector.

Accessibility software (screen readers, input method editors) relies on exactly this mechanism. WH_KEYBOARD hooks let input method editors intercept keystrokes before applications see them. WH_CBT hooks fire on window creation/destruction events and are used by UI automation frameworks.

Detection Methods Used by Security Software

Security software (anti-cheat engines, EDRs, AV products) uses a layered set of detection strategies. Understanding these is fundamental to building effective defenses:

  • API Monitoring (Kernel Callbacks): Windows provides kernel callbacks — PsSetCreateProcessNotifyRoutine, PsSetLoadImageNotifyRoutine — that fire whenever a process is created or a module is loaded. Anti-cheat drivers register these to inspect every DLL load in protected processes. LoadLibrary-based injection is trivially detectable this way.
  • Module List Comparison: The target process's loaded module list (the PEB's Ldr.InMemoryOrderModuleList) can be walked and compared against an expected whitelist. Unknown modules trigger an alert. Manual mapping evades this because it never registers with the loader.
  • Memory Scanning: Scanning all executable memory regions for PE headers (MZ magic, PE\0\0 signature) that do not correspond to any registered module. Manual-mapped DLLs are found this way if they preserve their PE header in the allocation.
  • Thread Start Address Inspection: Enumerating all threads in a process and checking each thread's start address (via NtQueryInformationThread with ThreadQuerySetWin32StartAddress). Threads created by CreateRemoteThread pointing at LoadLibraryA or an unknown allocation are highly suspicious.
  • Integrity Checks: Hashing the bytes of loaded modules against known-good values. If a DLL's code section has been modified in memory (e.g., hooks installed), the hash mismatch is detectable.
  • Return Address Validation: Inline checks that verify the call stack does not include frames from unexpected modules — if a hook has been placed on a game function, the return address will point into the injected DLL rather than the game binary.
// Simplified detection: scan for orphaned PE headers in executable memory
void ScanForUnregisteredModules(HANDLE hProcess)
{
    MEMORY_BASIC_INFORMATION mbi{};
    uintptr_t address = 0;
    const uint8_t MZ_MAGIC[] = { 0x4D, 0x5A }; // "MZ"

    while (VirtualQueryEx(hProcess, (LPCVOID)address, &mbi, sizeof(mbi))
           == sizeof(mbi))
    {
        if (mbi.State == MEM_COMMIT &&
            mbi.Type  == MEM_PRIVATE &&  // not MEM_IMAGE = not in module list
            (mbi.Protect & PAGE_EXECUTE_READ))
        {
            uint8_t header[2]{};
            SIZE_T  bytesRead = 0;
            ReadProcessMemory(hProcess, mbi.BaseAddress, header, 2, &bytesRead);

            if (bytesRead == 2 && memcmp(header, MZ_MAGIC, 2) == 0) {
                // Found a PE header in private executable memory — suspicious
                printf("[!] Possible injected module at %p\n", mbi.BaseAddress);
            }
        }
        address = (uintptr_t)mbi.BaseAddress + mbi.RegionSize;
    }
}

Legitimate Use Cases — Overlays, Modding, and Accessibility

DLL injection is not an inherently adversarial technique. Some of the most widely used software on Windows relies on it as a core architectural component:

  • Steam Overlay (GameOverlayRenderer64.dll): Injected into every Steam game to render the in-game overlay, handle the Shift+Tab shortcut, manage friend notifications, and enable screenshot capture. Uses a combination of SetWindowsHookEx and Direct3D/Vulkan present hook to intercept the swap chain.
  • Discord Overlay (DiscordHook64.dll): Injected to render voice chat indicators and notifications on top of game frames. Hooks DirectX and OpenGL present calls in the target process. Explicitly whitelisted by most anti-cheat systems.
  • NVIDIA GeForce Experience / NvCamera: Injects to enable the in-game performance overlay (Alt+Z), screenshot, and video capture. The NvCamera DLL hooks the graphics API within the game process.
  • RenderDoc: A graphics debugger widely used by game developers. Injects a capture DLL to intercept all D3D11/D3D12/Vulkan API calls, record GPU commands, and enable frame replay.
  • Script Extenders (SKSE, F4SE, etc.): The Skyrim Script Extender injects into the game process to extend the scripting engine with new functions, enabling the complex mod ecosystem. Entirely community-built and fully legitimate.
  • Screen Readers (NVDA, JAWS): Inject accessibility hooks into browsers and applications to read UI element text that is not exposed through standard Win32 accessibility APIs.
Key Takeaway:The technique itself is neutral — it is a documented capability of the Windows process model. Context and intent determine legitimacy. Understanding injection mechanics enables building better detection systems, evaluating anti-cheat effectiveness, and building tools that operate correctly alongside the many legitimate injectors already present in a typical gaming setup.
