Writing a Basic External Cheat in C++

A practical guide to external process memory tools using documented, public Windows API surfaces. All code here uses OpenProcess, ReadProcessMemory, WriteProcessMemory, and Toolhelp32 — standard Windows APIs.

Warning:Using these techniques against games with active anti-cheat in competitive multiplayer environments violates terms of service and may have legal consequences. Only run on systems you own or have explicit permission to analyze.

External vs Internal: Architecture Overview

Memory-based game tools fall into two architectural categories, each with distinct tradeoffs:

  • Internal (injected DLL) — a .dll is injected into the game's process and runs inside its address space. Direct memory access is trivial (just dereference a pointer), function hooking is straightforward, and performance is high. However, DLL injection is highly visible: anti-cheat scans the module list and checks code integrity.
  • External (separate process) — runs as a completely independent .exe. It reads and writes the game's memory via Windows kernel cross-process APIs (ReadProcessMemory /WriteProcessMemory). No code runs inside the game process. The handle to the game process is the attack surface — anti-cheat monitors who holds open handles with PROCESS_VM_READ orPROCESS_VM_WRITE access.

External tools are conceptually simpler and easier to study. They require only standard Windows headers (Windows.h, TlHelp32.h) and no special kernel drivers. From a defense perspective, understanding them helps game security engineers decide what handle access patterns to monitor.

Getting a Process Handle with OpenProcess

Everything starts with obtaining a handle to the target process. The Windows API function OpenProcess takes a desired access mask, an inheritance flag, and a process ID (PID). You first need to find the PID by enumerating running processes.

#include <Windows.h>
#include <TlHelp32.h>
#include <cstdint>
#include <string>
#include <stdexcept>

// Returns the PID of the first process matching processName (e.g., "game.exe")
DWORD GetProcessId(const std::wstring& processName) {
    HANDLE hSnap = CreateToolhelp32Snapshot(TH32CS_SNAPPROCESS, 0);
    if (hSnap == INVALID_HANDLE_VALUE)
        throw std::runtime_error("CreateToolhelp32Snapshot failed");

    PROCESSENTRY32W pe{};
    pe.dwSize = sizeof(pe);

    if (Process32FirstW(hSnap, &pe)) {
        do {
            if (processName == pe.szExeFile) {
                CloseHandle(hSnap);
                return pe.th32ProcessID;
            }
        } while (Process32NextW(hSnap, &pe));
    }

    CloseHandle(hSnap);
    return 0; // not found
}

// Open a handle with VM read/write access
HANDLE OpenGameProcess(DWORD pid) {
    HANDLE hProc = OpenProcess(
        PROCESS_VM_READ | PROCESS_VM_WRITE | PROCESS_QUERY_INFORMATION,
        FALSE,  // don't inherit handle
        pid
    );
    if (!hProc)
        throw std::runtime_error("OpenProcess failed — check privileges");
    return hProc;
}

// Usage:
// DWORD pid = GetProcessId(L"game.exe");
// HANDLE hProc = OpenGameProcess(pid);
Note:PROCESS_ALL_ACCESS is technically convenient but requests more rights than necessary and is more detectable. Prefer requesting only PROCESS_VM_READ | PROCESS_VM_WRITE | PROCESS_QUERY_INFORMATION— the principle of least privilege applies in security research too.

Reading Memory with ReadProcessMemory

ReadProcessMemory copies bytes from another process's virtual address space into your own buffer. The function signature is:

BOOL ReadProcessMemory(
    HANDLE  hProcess,        // handle obtained from OpenProcess
    LPCVOID lpBaseAddress,   // address in TARGET process to read from
    LPVOID  lpBuffer,        // your local buffer to receive the data
    SIZE_T  nSize,           // number of bytes to read
    SIZE_T* lpNumberOfBytesRead  // actual bytes read (can be NULL)
);

The ergonomic pattern is a templated wrapper so you can read any type cleanly:

// Generic typed read — returns T by value, zero-initialised on failure
template <typename T>
T Read(HANDLE hProc, uintptr_t address) {
    T value{};
    ReadProcessMemory(
        hProc,
        reinterpret_cast<LPCVOID>(address),
        &value,
        sizeof(T),
        nullptr
    );
    return value;
}

struct Vec3 { float x, y, z; };

// Reading concrete game values
float health   = Read<float> (hProc, playerBase + 0x0088);
float maxHp    = Read<float> (hProc, playerBase + 0x008C);
Vec3  position = Read<Vec3>  (hProc, playerBase + 0x0028);
int   teamNum  = Read<int>   (hProc, playerBase + 0x0090);
bool  isAlive  = Read<bool>  (hProc, playerBase + 0x0094);

printf("Pos: (%.1f, %.1f, %.1f)  HP: %.0f/%.0f  Team: %d\n",
       position.x, position.y, position.z,
       health, maxHp, teamNum);

For bulk reads (e.g., reading an entire entity struct at once to reduce syscall overhead), read the whole struct into a local shadow copy and then access fields from it — this is both faster and more cache-coherent:

#pragma pack(push, 1)  // match game's struct packing
struct PlayerEntity {
    uint8_t  _pad0[0x28];
    Vec3     vecOrigin;     // +0x28
    Vec3     vecVelocity;   // +0x34
    uint8_t  _pad1[0x50];
    float    flHealth;      // +0x88
    float    flMaxHealth;   // +0x8C
    int32_t  iTeamNum;      // +0x90
    bool     bAlive;        // +0x94
};
#pragma pack(pop)

PlayerEntity shadow = Read<PlayerEntity>(hProc, playerBase);
// Now access shadow.flHealth, shadow.vecOrigin, etc. locally — zero RPM calls

Writing Memory with WriteProcessMemory

WriteProcessMemory is the write counterpart. It requires the target memory page to be writable (PAGE_READWRITE or PAGE_EXECUTE_READWRITE). Heap-allocated game data is almost always writable; code pages are not (and modifying them is a separate, more involved topic).

// Generic typed write
template <typename T>
bool Write(HANDLE hProc, uintptr_t address, const T& value) {
    SIZE_T written = 0;
    return WriteProcessMemory(
        hProc,
        reinterpret_cast<LPVOID>(address),
        &value,
        sizeof(T),
        &written
    ) && written == sizeof(T);
}

// Modifying game state fields
float newHealth = 100.0f;
bool ok = Write<float>(hProc, playerBase + 0x0088, newHealth);

// Writing a Vec3 position (teleportation)
Vec3 newPos = { 512.0f, 0.0f, 128.0f };
Write<Vec3>(hProc, playerBase + 0x0028, newPos);

// Freeze health at max: write maxHealth value into health field
float maxHp = Read<float>(hProc, playerBase + 0x008C);
Write<float>(hProc, playerBase + 0x0088, maxHp);
Warning:Writing arbitrary values into game memory can cause crashes, undefined behavior, or server-side desync. The game server always maintains authoritative state in properly designed multiplayer architectures — writing client-side health to 100 will not change what the server believes your health to be. This is why server-side validation is the only real defense.

Finding the Module Base Address

To resolve static offsets (e.g., game.exe+0x01A2B3C0), you need the base address at which the game module was loaded. Use CreateToolhelp32Snapshot with TH32CS_SNAPMODULE to enumerate all modules loaded in the target process:

#include <Windows.h>
#include <TlHelp32.h>
#include <cstdint>
#include <string>

// Returns the base load address of a named module within a remote process
uintptr_t GetModuleBase(DWORD pid, const std::wstring& moduleName) {
    HANDLE hSnap = CreateToolhelp32Snapshot(
        TH32CS_SNAPMODULE | TH32CS_SNAPMODULE32,  // include 32-bit modules too
        pid
    );
    if (hSnap == INVALID_HANDLE_VALUE)
        return 0;

    MODULEENTRY32W me{};
    me.dwSize = sizeof(me);

    uintptr_t base = 0;
    if (Module32FirstW(hSnap, &me)) {
        do {
            if (moduleName == me.szModule) {
                base = reinterpret_cast<uintptr_t>(me.modBaseAddr);
                break;
            }
        } while (Module32NextW(hSnap, &me));
    }

    CloseHandle(hSnap);
    return base;
}

// Example: resolve a static pointer stored at a fixed offset from game.exe
uintptr_t gameBase = GetModuleBase(pid, L"game.exe");

// Read the entity manager pointer (a static global at moduleBase + offset)
constexpr uintptr_t OFFSET_ENTITY_MGR = 0x01A2B3C0;
uintptr_t entityMgr = Read<uintptr_t>(hProc, gameBase + OFFSET_ENTITY_MGR);

// Follow the pointer chain to the local player
uintptr_t localPlayer = Read<uintptr_t>(hProc, entityMgr + 0x0);
localPlayer = Read<uintptr_t>(hProc, localPlayer + 0x58);

Note that TH32CS_SNAPMODULE32 is needed to see 32-bit modules from a 64-bit snapshot process. Omitting it causes Module32FirstW to miss modules in WoW64 games.

Building a Simple Read Loop

Putting it all together, a tool typically runs in a loop — resolving pointers each iteration (since game objects are reallocated between rounds) and sleeping between reads to avoid hammering the kernel with unnecessary RPM calls. Here is a minimal but complete example:

#include <Windows.h>
#include <TlHelp32.h>
#include <cstdint>
#include <cstdio>
#include <thread>
#include <chrono>

// ── Forward declarations (implementations shown in earlier sections) ───────
DWORD    GetProcessId(const std::wstring& name);
HANDLE   OpenGameProcess(DWORD pid);
uintptr_t GetModuleBase(DWORD pid, const std::wstring& mod);

template <typename T> T    Read (HANDLE h, uintptr_t a);
template <typename T> bool Write(HANDLE h, uintptr_t a, const T& v);

struct Vec3 { float x, y, z; };

// ── Offsets ────────────────────────────────────────────────────────────────
namespace off {
    constexpr uintptr_t entityMgrPtr = 0x01A2B3C0; // module-relative static ptr
    constexpr uintptr_t vecOrigin    = 0x0028;
    constexpr uintptr_t flHealth     = 0x0088;
    constexpr uintptr_t iTeamNum     = 0x0090;
    constexpr uintptr_t bAlive       = 0x0094;
}

// ── Main loop ─────────────────────────────────────────────────────────────
int main() {
    const std::wstring PROC_NAME = L"game.exe";
    const int POLL_MS = 16; // ~60 Hz update rate

    HANDLE   hProc    = nullptr;
    uintptr_t modBase = 0;
    DWORD    pid      = 0;

    puts("[*] Waiting for game process...");

    // Wait until game launches
    while (!(pid = GetProcessId(PROC_NAME)))
        std::this_thread::sleep_for(std::chrono::seconds(1));

    hProc   = OpenGameProcess(pid);
    modBase = GetModuleBase(pid, PROC_NAME);
    printf("[+] Attached. PID=%lu  ModBase=0x%llX\n", pid, (unsigned long long)modBase);

    while (true) {
        // Re-resolve pointer chain each tick (handles game restarts / reloads)
        uintptr_t entityMgr  = Read<uintptr_t>(hProc, modBase + off::entityMgrPtr);
        uintptr_t localPlayer = Read<uintptr_t>(hProc, entityMgr + 0x0);
        localPlayer           = Read<uintptr_t>(hProc, localPlayer + 0x58);

        if (!localPlayer) {
            puts("[-] LocalPlayer not found (in menu?)");
            std::this_thread::sleep_for(std::chrono::milliseconds(500));
            continue;
        }

        Vec3  pos    = Read<Vec3> (hProc, localPlayer + off::vecOrigin);
        float health = Read<float>(hProc, localPlayer + off::flHealth);
        int   team   = Read<int>  (hProc, localPlayer + off::iTeamNum);
        bool  alive  = Read<bool> (hProc, localPlayer + off::bAlive);

        // Clear line and print telemetry
        printf("\r[+] Pos=(%.1f,%.1f,%.1f)  HP=%.0f  Team=%d  Alive=%s    ",
               pos.x, pos.y, pos.z, health, team, alive ? "Y" : "N");
        fflush(stdout);

        std::this_thread::sleep_for(std::chrono::milliseconds(POLL_MS));
    }

    CloseHandle(hProc);
    return 0;
}

This loop re-resolves the full pointer chain on every tick. While slightly redundant (pointers rarely change mid-game), it makes the tool robust across scene transitions, map loads, and game restarts without requiring any special handling. In a more optimized version, you would cache the resolved localPlayer pointer and only re-resolve it when a read returns zero or the process memory map changes.

Note:Compile with MSVC or MinGW targeting x64 (-m64). Link against no special libraries — onlykernel32.lib (implicit). Run as Administrator if OpenProcess fails due to insufficient privileges. The SeDebugPrivilege token privilege can be enabled programmatically for elevated access without running as admin, though this itself requires the token to already have the privilege assigned.
