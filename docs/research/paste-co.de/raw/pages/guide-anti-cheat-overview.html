How Game Anti-Cheat Systems Work — Technical Overview

Anti-cheat systems are among the most technically complex software deployed to consumer machines — they operate at the intersection of operating system internals, cryptography, behavioral analysis, and network security. This guide is a technically accurate survey of how the major systems work, based on publicly documented behavior, security research publications, and disclosed information from the vendors themselves.

Categories of Anti-Cheat

Anti-cheat systems are commonly classified along two axes: where detection runs (client vs server) andwhat privilege level the client component operates at.

  • User-mode client-side (Ring 3) — runs as a normal application process or loaded DLL within the game process. Can inspect other user-space processes, read the file system, and query Windows APIs. Limited by the fact that sophisticated tools can operate at a lower ring level and remain invisible. Examples: early VAC versions, PunkBuster era.
  • Kernel-mode client-side (Ring 0) — installs a kernel driver (.sys file) that operates with full OS privileges. Can inspect any process, hook system calls, access hardware-level features, and detect tampering that user-mode tools cannot see. The modern standard for competitive games. Examples: Riot Vanguard, FACEIT AC, BattlEye (current), EAC (kernel mode available).
  • Server-side — validation logic runs on the authoritative game server. Analyzes player statistics, trajectory data, shot patterns, and physics consistency. Cannot be bypassed by any client modification. The only reliable long-term defense but requires significant engineering investment. Examples: Valve Overwatch, statistical ban systems.
  • Hybrid — all modern serious anti-cheat systems use a combination: kernel-mode client component for immediate detection + server-side analysis for statistical validation + delayed ban waves to prevent cheaters from pinpointing what triggered detection.

EasyAntiCheat (EAC) — Detection Mechanisms

EasyAntiCheat (now owned by Epic Games) is one of the most widely deployed anti-cheat systems, used in titles including Fortnite, Apex Legends, Rust, and hundreds of others. Its architecture has evolved significantly from its early user-mode-only implementation.

Process and Module Scanning

EAC enumerates the running process list and loaded module list of the game process using the same Toolhelp32 and PSAPI APIs available to user-mode code. It checks loaded modules against an allowlist and flags any unrecognized DLL injected into the game's address space. It also inspects process names and window titles of other running applications against a blocklist of known cheat tools and debuggers.

Memory Integrity Verification

EAC periodically checksums the game's own code sections (.text segment of the main executable and key DLLs) to detect runtime code patching. Any byte modification — including INT3 software breakpoints — will trigger a mismatch. The checksums are sent to EAC's cloud backend for server-side verification, preventing simple checksum spoofing.

Driver Signing and Kernel Mode

Modern EAC optionally deploys a kernel-mode driver (EasyAntiCheat.sys). This driver is WHQL-signed and requires Windows Driver Signature Enforcement to be active. It monitors handle access to the game process from external processes — specifically watching for PROCESS_VM_READ or PROCESS_VM_WRITE access granted to non-system processes. From kernel mode, it can also enumerate loaded kernel drivers and detect unauthorized drivers that may be providing privileged memory access.

// EAC kernel driver conceptually instruments ObRegisterCallbacks
// to monitor process handle creation — something like:

OB_PREOP_CALLBACK_STATUS HandleCallback(
    PVOID RegistrationContext,
    POB_PRE_OPERATION_INFORMATION OpInfo)
{
    if (OpInfo->ObjectType == *PsProcessType) {
        PEPROCESS targetProcess = (PEPROCESS)OpInfo->Object;

        // If someone is opening a handle to the game process...
        if (targetProcess == g_GameProcess) {
            // Strip VM read/write access from the requested access mask
            // unless the requester is a trusted system process
            OpInfo->Parameters->CreateHandleInformation.DesiredAccess
                &= ~(PROCESS_VM_READ | PROCESS_VM_WRITE);
        }
    }
    return OB_PREOP_SUCCESS;
}

BattlEye — Architecture and Detection

BattlEye (BE) is used in Escape from Tarkov, DayZ, Rainbow Six Siege, PUBG, and many others. It is known for aggressive kernel-mode detection and has been publicly documented by researchers and the BE team itself.

Ring-0 Driver and Historical SSDT Hooks

In earlier versions, BattlEye's kernel driver hooked the System Service Descriptor Table (SSDT) — a table of pointers to native NT system call handlers. By replacing entries for calls like NtOpenProcess, NtReadVirtualMemory, and NtWriteVirtualMemory, BE could intercept any attempt to access the game process from user mode and block or log the call. Microsoft's introduction of PatchGuard (Kernel Patch Protection, KPP) in x64 Windows made SSDT hooking incompatible with modern systems — PatchGuard periodically verifies the integrity of the SSDT and BSODs the system if modifications are detected.

Modern PatchGuard-Aware Approach

Current BattlEye uses the documented ObRegisterCallbacks API (same as EAC above) rather than SSDT hooks, making it fully PatchGuard-compatible. It also uses PsSetLoadImageNotifyRoutine to be notified every time any image (driver, DLL, executable) is loaded system-wide — this catches driver-based cheating tools before they can establish themselves. Additionally, BE scans physical memory for known cheat signatures using mapped kernel memory and MmMapIoSpace-style operations.

Communication and Updates

BattlEye employs a dynamic update mechanism — its core scanning logic is downloaded in encrypted, obfuscated form at game startup and changes frequently. This makes static signature-based evasion quickly obsolete. The driver maintains a persistent encrypted channel to BE's cloud backend for log submission and scan data upload.

VAC — Steam's Approach

Valve Anti-Cheat (VAC) is distinct from EAC and BattlEye in philosophy: it deliberately prioritizes false-positive avoidance over instant detection. VAC operates entirely in user mode and is known for several characteristic behaviors documented through Valve's own statements and security research.

Offline / Asynchronous Scanning

VAC does not rely on real-time kernel monitoring. Instead, it runs periodic scans of the game process and the system during play sessions. Scan modules are downloaded from Valve's content delivery network, executed, and the results are sent to Valve's backend servers for analysis — the client never knows which specific checks are being run at any given time.

Hash-Based Detection

VAC's most well-documented detection mechanism is hash-based: it computes cryptographic hashes of DLLs and executables on disk and in memory. Known cheat binaries and game modification libraries are matched against a server-side database of malicious hashes. Because this operates on file hashes, trivial recompilation or binary patching of a cheat can sometimes evade it — Valve counters this by maintaining a large and continuously updated hash database.

Delayed Bans

VAC is famous for "ban waves" — detections are logged but bans are not issued immediately. Valve has historically issued bans weeks or months after initial detection. This serves multiple purposes: it prevents cheaters from determining exactly which action triggered detection, it allows Valve to accumulate enough evidence to ensure confidence, and it disrupts the cheat-development feedback loop (cheaters cannot quickly test whether a modification evades detection).

Note:VAC bans are permanent and tied to the Steam account, not hardware. A VAC ban restricts the account from playing VAC-secured servers in the banned game. Valve does not communicate specific reasons for bans, which is intentional — revealing detection specifics would allow evasion.

Kernel-Level Anti-Cheat — Vanguard and FACEIT

Riot Vanguard (used in Valorant, League of Legends) and FACEIT Anti-Cheat represent the most invasive category of anti-cheat currently deployed to consumer systems. They run kernel drivers that start at Windows boot — not only when the game is running — giving them the maximum possible vantage point.

Why Ring-0?

The fundamental reason for kernel-mode operation is that any user-mode anti-cheat can be defeated by a kernel-mode cheat. A driver running at ring-0 can hide processes from the task manager, make DLLs invisible to module enumeration APIs, and intercept memory reads at the hardware page-table level using techniques like DKOM (Direct Kernel Object Manipulation). Running the anti-cheat in the kernel places it on equal footing with the most sophisticated attack tools.

Vanguard's Boot-Time Driver

vgk.sys (Vanguard's kernel component) starts as a boot-start driver — it is initialized by Windows during the kernel boot phase, before any user session begins. This means it is active before any cheat tool could load. It uses ObRegisterCallbacks to protect Valorant's process, monitors for unsigned or improperly signed drivers, and hooks into Windows security callbacks to detect kernel exploits. Vanguard requires Secure Boot and TPM 2.0 (enforced in Windows 11) to prevent tampering with the boot chain itself — a bootkit could otherwise load before vgk.sys.

TPM and Secure Boot Requirements

Trusted Platform Module (TPM) and Secure Boot together create a hardware root of trust. Secure Boot ensures only Microsoft-signed bootloaders execute, preventing bootkits. TPM can be used for hardware fingerprinting — binding a ban to the physical machine rather than just an account. Riot's requirement for these features in Valorant was controversial but reflects a genuine security rationale: without a hardware root of trust, a sufficiently motivated attacker can bypass any software-only protection by booting a modified OS.

// Conceptual: kernel driver checking for unsigned drivers using
// PsSetLoadImageNotifyRoutine callback

VOID ImageLoadCallback(
    PUNICODE_STRING FullImageName,
    HANDLE          ProcessId,       // 0 = kernel driver load
    PIMAGE_INFO     ImageInfo)
{
    if (ProcessId == 0) {
        // A kernel driver is loading
        // Verify the image has a valid Microsoft WHQL or EV code signing cert
        NTSTATUS status = VerifyImageSignature(FullImageName);
        if (!NT_SUCCESS(status)) {
            // Log the unsigned driver load attempt
            LogSuspiciousDriver(FullImageName, ImageInfo->ImageBase);
            // Anti-cheat may choose to block the game from launching,
            // or flag the session for server-side review
        }
    }
}

Server-Side Validation — The Real Defense

The security research community broadly agrees on a fundamental principle: client-side anti-cheat alone is never sufficient. Because the cheat operator controls the physical hardware and operating system, any client-side protection can theoretically be defeated given enough time and resources. The only architecturally sound defense is server-side authoritative validation.

What Server-Side Validation Means in Practice

  • Authoritative physics — the server computes all game state. Clients submit inputs (key presses, mouse movement) and the server determines outcomes. A client reporting "I shot and hit" is meaningless — the server independently validates whether the shot trajectory was geometrically possible given both players' positions.
  • Statistical anomaly detection — the server logs headshot rates, reaction times, tracking smoothness, and pre-fire patterns. Machine learning models identify statistical distributions inconsistent with human performance. This catches subtle aim assistance that pixel-perfect pattern matching cannot.
  • Rate limiting and input validation — the server rejects inputs that are physically impossible (movement faster than max speed, actions faster than frame rate, etc.). Writing a speed value into client memory has no effect if the server rejects the resulting movement as impossible.
  • Replay analysis — server-recorded replays can be analyzed offline using automated tools and human review (Valve's Overwatch system) to flag suspicious sessions after the fact.

The most technically sophisticated cheats — those that operate entirely in kernel space, use DMA (Direct Memory Access) hardware to read game memory from a second PC without touching the game process, or run AI-based visual input processing via external GPU capture — are fundamentally immune to any client-side detection. A DMA-based setup has no footprint on the target machine whatsoever. Against these threats, server-side behavioral analysis is the only viable defense layer.

Key Takeaway:The security engineering lesson from studying anti-cheat systems is that defense-in-depth matters. Kernel-mode client anti-cheat catches the broad population of script-kiddie level tools. Statistical server-side analysis catches sophisticated actors. Neither layer alone is sufficient — both are necessary, and they complement each other by operating on different parts of the threat surface.
