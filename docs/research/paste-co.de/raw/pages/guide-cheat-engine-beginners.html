Cheat Engine Tutorial for Beginners — Find & Modify Game Values

Cheat Engine is a free, open-source memory scanner and debugger used extensively in game modding and security research. This guide walks through the fundamentals: finding values in memory, narrowing results, freezing addresses, and building reusable trainer tables.

What Is Cheat Engine?

Cheat Engine (CE) is a multi-purpose tool originally written by Eric Heijnen ("Dark Byte"). At its core it is a memory scanner — it attaches to a running process and allows you to read, search, and write values anywhere in that process's virtual address space. Beyond scanning, it includes:

  • Debugger: A built-in x86/x64 debugger with breakpoints, step execution, and an assembler/disassembler (based on BeaEngine). You can pause a process mid-frame and inspect exactly which instruction wrote to an address.
  • Trainer Maker: Once you have stable addresses or pointer chains, CE lets you package them into a .CT (Cheat Table) file — a shareable XML document that encodes all your findings along with optional Lua scripts and hotkeys.
  • Structure Dissector: A tool for reverse-engineering in-memory C++ objects and structs by grouping contiguous addresses and watching which offsets change together.
  • Speed Hacks: CE can hook the Windows timer or the game's own timing functions to slow or accelerate execution — useful for frame-by-frame debugging.
Note:All techniques described here are for use on processes you own or have permission to analyze — such as single-player games you purchased, or purpose-built research environments. Studying memory structures is a core skill in game modding and security research.

First Scan: Finding a Value

The most common workflow begins with an Exact Value scan. Suppose your character has 250 HP displayed on screen. Open Cheat Engine, attach to the game process via the process selector, then:

  1. Set the Value Type to 4 Bytes (most game integers are 32-bit). If the value could be a float (e.g., 250.0f), choose Float.
  2. Set Scan Type to Exact Value.
  3. Type 250 in the value field and click First Scan. CE will read every committed memory page in the process and collect all addresses that currently hold the value 250.
  4. The results list may return thousands of hits — this is expected. Every variable that happens to equal 250 at this moment is included.

If you do not know the starting value — for example the health is shown as a bar but not a number — use the Unknown Initial Value scan type. CE takes a snapshot of all memory without filtering and records every address as a candidate. Subsequent scans then filter based on how values have changed relative to the snapshot.

Scan Type: Exact Value      → knows the current number
Scan Type: Unknown Initial  → no idea what the number is
Value Type: 4 Bytes         → 32-bit signed integer (most common)
Value Type: Float           → 32-bit IEEE 754 float  (e.g. 250.0)
Value Type: 8 Bytes         → 64-bit integer (modern engines)
Value Type: 2 Bytes         → 16-bit (older engines, inventory counts)

Narrowing Down Results

After the first scan you typically have far too many candidates. The trick is to change the game state — take some damage, heal, spend gold — and then run a Next Scan with a refined criterion. Repeat until only a handful of addresses remain.

  • Exact Value: You know the new precise value (e.g., after taking 30 damage, scan for 220). Eliminates everything that is not exactly 220 now.
  • Decreased Value: You know the value went down but not by how much (health dropped, money spent). Keeps addresses whose current value is lower than the snapshot.
  • Increased Value: The value went up (experience gained, item collected). Keeps addresses higher than snapshot.
  • Decreased By: You know the exact delta. Took 30 damage? Decreased By 30. Very precise — cuts results dramatically.
  • Increased By: Gained exactly 500 gold? Increased By 500.
  • Unchanged Value: Nothing happened between scans — keeps only addresses that have stayed the same. Use between action events to rule out noise.
  • Changed Value: Anything different from the snapshot — useful when you cannot control the change but know something changed.

A typical session: First Scan (exact 250) → take 30 damage → Next Scan (exact 220) → heal 50 → Next Scan (exact 270). After two or three iterations you should have 1–5 addresses remaining. The address that consistently follows your character's HP is your target.

Tip:Right-click any result and choose Browse this memory region to open the hex editor at that address. Nearby bytes often reveal adjacent fields in the same struct (e.g., mana right after HP).

The Address List and Freezing Values

Once you have found the correct address, double-click it (or press the red arrow button) to add it to the Address List at the bottom of the CE window. This list is your workspace — you can rename entries, change their value, and most importantly freeze them.

Freezing works by ticking the checkbox next to an entry. When frozen, CE's background thread repeatedly writes your chosen value back to that address at a high frequency (default ~30 writes/sec). The game's own code may still decrement HP, but CE immediately overwrites it — effectively making the value appear static.

Address List workflow:
  1. Double-click result → appears in address list with current value
  2. Double-click the "Value" column → type a new value → press Enter
     The game memory is immediately written with your new value.
  3. Tick the checkbox → value is now FROZEN (CE rewrites it continuously)
  4. Right-click entry → "Change record" → rename it (e.g. "Player HP")
  5. Right-click entry → "Set/remove hotkey" → assign a key to toggle freeze

You can also set a freeze type: some entries should only ever increase (e.g., a resource you want to accumulate) or only decrease. Right-click and choose Change freeze type to control direction.

Pointer Scanning — Why Addresses Break and How Pointer Chains Solve It

The address you found with scanning is a dynamic heap address. Every time you restart the game, the memory allocator places game objects at different locations. Your saved address becomes invalid — you have to scan all over again.

The solution is a pointer chain. The game engine itself maintains stable, static pointers (usually in the .data segment of the EXE or a DLL) that eventually lead to the dynamic object you care about. A pointer chain looks like this:

Static base address (always the same, e.g. "game.exe"+0x12A4F0)
  → points to a Player Manager object at 0x1A3C0000
  + offset 0x58  → points to local Player object at 0x1A3C8800
  + offset 0x10C → the HP integer value

In CE address list notation:
  [["game.exe"+0x12A4F0]+0x58]+0x10C

To find this chain, use CE's built-in Pointer Scanner:

  1. With your dynamic HP address in the address list, right-click it and choose Pointer scan for this address.
  2. Configure max level (depth of chain, typically 4–6) and max offset per level (usually 0x500 or 0x1000). Leave only static base addresses checked.
  3. Save the scan result (.ptr file). CE will enumerate thousands of candidate chains.
  4. Restart the game, reopen the .ptr file, and run Rescan pointer with the new dynamic address for HP. Any chain that still resolves correctly across restarts is valid.
  5. After two or three restarts, you will typically be left with one or a few valid chains. Add the shortest one (fewest offsets) to your address list — it is the most stable.
Note:You can also use CE's "Find out what writes to this address" debugger feature to locate the instruction that modifies HP. This instruction is in compiled game code at a stable offset from the module base — which gives you an even more reliable anchor point for reverse engineering the surrounding data structures.

Creating a Cheat Table (.CT File) and Sharing It

A Cheat Table (.CT) is a compressed XML file that stores your entire CE session: address list entries, pointer chains, Lua scripts, and hotkey bindings. It is the standard distribution format for CE-based mods.

To save a table: File → Save. To load one someone else made: File → Open then attach to the target process. CE will automatically resolve all pointer chains relative to the current session.

<!-- Simplified .CT XML structure (inside the compressed file) -->
<CheatTable>
  <CheatEntries>
    <CheatEntry>
      <Description>Player HP</Description>
      <VariableType>4 Bytes</VariableType>
      <Address>"game.exe"+12A4F0</Address>
      <Offsets>
        <Offset>10C</Offset>   <!-- last offset applied first -->
        <Offset>58</Offset>
      </Offsets>
      <CheatType>1</CheatType>  <!-- 1 = frozen -->
      <CustomValue>9999</CustomValue>
    </CheatEntry>
  </CheatEntries>
  <LuaScript>
    -- Runs when the table activates
    print("Table loaded for MyGame v1.2")
  </LuaScript>
</CheatTable>

CE's embedded Lua engine (Lua 5.3) lets you write activation scripts that auto-attach to processes, read addresses dynamically, create custom UI forms, and react to game events. Complex tables for modern games are essentially small Lua programs layered on top of CE's scanning infrastructure.

Community tables are shared on sites like FearLess Cheat Engine and the official CE forum. When studying a published table, examining the Lua scripts and pointer chains is an excellent way to understand how experienced researchers structure their findings — and how to extend them to newer game versions when offsets shift after an update.

Further Reading:Cheat Engine ships with a built-in tutorial process (Help → Cheat Engine Tutorial) that guides you through 8 progressively harder scanning challenges, including pointer levels and code injection. Working through all 8 steps is the fastest way to build foundational fluency.
