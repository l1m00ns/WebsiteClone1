Introduction to Windows Kernel Drivers — How They Work

Windows kernel drivers are native code modules that execute in the most privileged environment of the operating system. Understanding how they are structured is fundamental for game security researchers, anti-cheat engineers, and low-level systems developers. This guide covers the conceptual and practical foundations.

User Mode vs. Kernel Mode — Ring 3 vs. Ring 0

Modern x86-64 CPUs implement four privilege rings (0–3). Windows uses only two in practice:

  • Ring 3 (User Mode): Where all standard applications run — browsers, games, your own executables. Code here is sandboxed: each process gets its own virtual address space, and the CPU prevents direct hardware access. Attempts to execute privileged instructions (like IN, OUT, or LGDT) cause a General Protection Fault and the OS kills the process. Win32 API calls that need kernel services cross into Ring 0 via a syscall instruction, which traps into the kernel.
  • Ring 0 (Kernel Mode): Where the Windows Executive, HAL, and all kernel-mode drivers run. Code here can access any physical memory address, execute any instruction, and manipulate CPU control registers. A single bad pointer dereference at Ring 0 triggers a Blue Screen of Death (BSOD) — there is no safety net.

From a research perspective, Ring 0 access means you can read or write any process's memory without the target process being aware, hook system calls before they are processed, and interact with hardware directly. This is why anti-cheat software often runs kernel drivers — they operate at the same privilege level they are protecting against.

User Mode (Ring 3)                   Kernel Mode (Ring 0)
────────────────────                 ──────────────────────────────
Your game process                    ntoskrnl.exe  (Windows Executive)
Discord overlay DLL                  hal.dll       (Hardware Abstraction)
System DLLs (ntdll, kernel32)        Driver1.sys, Driver2.sys ...
                    ↕ syscall / DeviceIoControl ↕
        Transition via software interrupt or SYSCALL instruction

Driver Types: WDM, KMDF, and UMDF

Microsoft has evolved its driver framework over the decades. Choosing the right model matters for both functionality and stability:

  • WDM (Windows Driver Model): The foundational layer — raw access to kernel APIs. You manage your own IRPs (I/O Request Packets), device objects, and dispatch routines manually. Maximum flexibility, maximum responsibility. Most legacy drivers and research/proof-of-concept drivers use WDM because it has the fewest abstractions. If something goes wrong, it is your fault entirely.
  • KMDF (Kernel-Mode Driver Framework): A structured framework built on top of WDM. KMDF abstracts the IRP lifecycle, power management, plug-and-play events, and synchronization primitives into callback-based objects (WDFDEVICE, WDFQUEUE, WDFREQUEST). It dramatically reduces boilerplate and common crash vectors. Use KMDF for any production driver where you do not specifically need WDM's raw control.
  • UMDF (User-Mode Driver Framework): Drivers that run in user space but appear as kernel drivers to the I/O manager. Suitable for protocol drivers, USB HID devices, and sensors where a crash should not BSOD the machine. Cannot read arbitrary process memory or interact with kernel structures — not applicable to security research scenarios.
Recommendation:For security research and game tooling, start with WDM to understand the raw primitives. Once comfortable, migrate to KMDF for any code you intend to ship — it handles dozens of edge cases (cancel-safe queues, reference counting, device removal) automatically.

Setting Up the Windows Driver Kit (WDK) with Visual Studio

Driver development requires a matched pair of Visual Studio and the Windows Driver Kit (WDK). Both versions must align exactly — a WDK for Windows 11 24H2 will not work against a Windows 10 SDK.

  1. Install Visual Studio 2022 with the Desktop development with C++ workload. Ensure the Windows SDK component is checked (version 10.0.22621 or later for modern targets).
  2. Download the WDK from learn.microsoft.com/windows-hardware/drivers/download-the-wdk. Run the installer — it will offer to install the VS extension automatically.
  3. In Visual Studio, create a new project → search for "Kernel Mode Driver, Empty (KMDF)" or "Kernel Mode Driver, Empty (WDM)". The templates set up the correct compiler flags (/kernel, floating-point restrictions) and linker settings (/DRIVER:WDM, entry point DriverEntry).
  4. Set up a test VM (Hyper-V or VMware) running Windows. Enable kernel debugging over a network or COM port. Never test experimental drivers on your development host — a BSOD loop can corrupt the filesystem.
# In the test VM — enable kernel debugging over network (kdnet):
bcdedit /debug on
bcdedit /dbgsettings net hostip:<DEV_MACHINE_IP> port:50000 key:1.2.3.4

# On the dev machine — attach WinDbg Preview:
# File → Kernel Debug → Net → fill in port and key

A Minimal Driver Skeleton — DriverEntry and Unload

Every kernel driver must export a DriverEntry function — the kernel calls this once when the driver is loaded, analogous to main() in a user-mode application. Below is the smallest correct WDM driver that creates a device, registers a symbolic link (so user-mode can open it), and cleans up on unload.

// minimal_driver.c
#include <ntddk.h>

#define DEVICE_NAME   L"\\Device\\MinimalDriver"
#define SYMLINK_NAME  L"\\DosDevices\\MinimalDriver"

PDEVICE_OBJECT g_DeviceObject = NULL;

// Called when the driver is unloaded (e.g., sc stop MinimalDriver)
VOID DriverUnload(PDRIVER_OBJECT DriverObject)
{
    UNREFERENCED_PARAMETER(DriverObject);

    // Remove the symbolic link so user-mode can no longer open it
    UNICODE_STRING symlinkName;
    RtlInitUnicodeString(&symlinkName, SYMLINK_NAME);
    IoDeleteSymbolicLink(&symlinkName);

    // Delete the device object
    if (g_DeviceObject)
        IoDeleteDevice(g_DeviceObject);

    DbgPrint("[MinimalDriver] Unloaded.\n");
}

// Handles IRP_MJ_CREATE and IRP_MJ_CLOSE — just complete them successfully
NTSTATUS DispatchCreateClose(PDEVICE_OBJECT DeviceObject, PIRP Irp)
{
    UNREFERENCED_PARAMETER(DeviceObject);
    Irp->IoStatus.Status      = STATUS_SUCCESS;
    Irp->IoStatus.Information = 0;
    IoCompleteRequest(Irp, IO_NO_INCREMENT);
    return STATUS_SUCCESS;
}

// Kernel entry point — runs at IRQL PASSIVE_LEVEL
NTSTATUS DriverEntry(PDRIVER_OBJECT DriverObject, PUNICODE_STRING RegistryPath)
{
    UNREFERENCED_PARAMETER(RegistryPath);

    DbgPrint("[MinimalDriver] Loading...\n");

    // Register the unload routine (without this, the driver cannot be stopped)
    DriverObject->DriverUnload = DriverUnload;

    // Register dispatch routines for open/close
    DriverObject->MajorFunction[IRP_MJ_CREATE] = DispatchCreateClose;
    DriverObject->MajorFunction[IRP_MJ_CLOSE]  = DispatchCreateClose;

    // Create the device object
    UNICODE_STRING deviceName;
    RtlInitUnicodeString(&deviceName, DEVICE_NAME);

    NTSTATUS status = IoCreateDevice(
        DriverObject,
        0,                        // DeviceExtension size (0 = none)
        &deviceName,
        FILE_DEVICE_UNKNOWN,
        FILE_DEVICE_SECURE_OPEN,
        FALSE,                    // not exclusive
        &g_DeviceObject
    );

    if (!NT_SUCCESS(status)) {
        DbgPrint("[MinimalDriver] IoCreateDevice failed: 0x%X\n", status);
        return status;
    }

    // Create symbolic link accessible from user mode as \\.\MinimalDriver
    UNICODE_STRING symlinkName;
    RtlInitUnicodeString(&symlinkName, SYMLINK_NAME);

    status = IoCreateSymbolicLink(&symlinkName, &deviceName);
    if (!NT_SUCCESS(status)) {
        IoDeleteDevice(g_DeviceObject);
        return status;
    }

    DbgPrint("[MinimalDriver] Loaded successfully.\n");
    return STATUS_SUCCESS;
}

The DRIVER_OBJECT structure passed into DriverEntry is the kernel's representation of your driver. Populating its MajorFunction dispatch table — an array of 28 function pointers indexed by IRP major code — is how you register handlers for all I/O operations (create, read, write, IOCTL, cleanup, close, etc.).

IOCTL Communication — User Mode to Kernel Mode

The standard mechanism for a user-mode application to send commands to a kernel driver is IOCTL (I/O Control Code). The user side calls DeviceIoControl(); the kernel dispatch routine for IRP_MJ_DEVICE_CONTROL receives the call with a structured IRP.

// Shared header (used by both driver and user-mode app)
// shared.h
#pragma once
#include <Windows.h>   // user side; use <ntddk.h> equivalent in driver

// CTL_CODE macro: DeviceType | Function | Method | Access
#define IOCTL_READ_MEMORY  CTL_CODE(FILE_DEVICE_UNKNOWN, 0x800, \
                                    METHOD_BUFFERED, FILE_ANY_ACCESS)

typedef struct _READ_REQUEST {
    ULONG_PTR TargetPid;
    ULONG_PTR Address;
    SIZE_T    Size;
} READ_REQUEST, *PREAD_REQUEST;

// ── Kernel-side IOCTL handler ─────────────────────────────────────────────
NTSTATUS DispatchIoControl(PDEVICE_OBJECT DeviceObject, PIRP Irp)
{
    UNREFERENCED_PARAMETER(DeviceObject);

    PIO_STACK_LOCATION stack = IoGetCurrentIrpStackLocation(Irp);
    ULONG code  = stack->Parameters.DeviceIoControl.IoControlCode;
    ULONG inLen = stack->Parameters.DeviceIoControl.InputBufferLength;

    NTSTATUS status = STATUS_INVALID_DEVICE_REQUEST;
    ULONG_PTR info  = 0;

    if (code == IOCTL_READ_MEMORY && inLen >= sizeof(READ_REQUEST))
    {
        PREAD_REQUEST req = (PREAD_REQUEST)Irp->AssociatedIrp.SystemBuffer;
        // ... locate target process, call MmCopyVirtualMemory, etc.
        status = STATUS_SUCCESS;
        info   = req->Size;
    }

    Irp->IoStatus.Status      = status;
    Irp->IoStatus.Information = info;
    IoCompleteRequest(Irp, IO_NO_INCREMENT);
    return status;
}

// ── User-mode app side ────────────────────────────────────────────────────
// user_app.c  (compiled as regular Win32 executable)
HANDLE hDriver = CreateFile(L"\\\\.\\MinimalDriver",
    GENERIC_READ | GENERIC_WRITE, 0, NULL,
    OPEN_EXISTING, FILE_ATTRIBUTE_NORMAL, NULL);

READ_REQUEST req = { .TargetPid = targetPid,
                     .Address   = 0x7FF600000000ULL,
                     .Size      = 4 };
DWORD bytesReturned = 0;
DeviceIoControl(hDriver, IOCTL_READ_MEMORY,
    &req, sizeof(req),
    outputBuf, sizeof(outputBuf),
    &bytesReturned, NULL);

The METHOD_BUFFERED transfer type (the third field of CTL_CODE) tells the I/O manager to copy both the input and output buffers into a single kernel-allocated buffer (Irp->AssociatedIrp.SystemBuffer), which you access safely from your dispatch routine. Other methods (METHOD_IN_DIRECT, METHOD_NEITHER) give different tradeoffs between safety and performance.

Test Signing vs. Production Signing

Since Windows Vista 64-bit, the kernel enforces Driver Signature Enforcement (DSE): every .sys file loaded by the kernel must be signed by a trusted certificate authority. Unsigned drivers are blocked before DriverEntry is ever called.

  • Test Mode: Allows drivers signed with any self-signed certificate (created via makecert or the WDK's signtool). Enable it in the test VM with:
    bcdedit /set testsigning on
# Reboot required. A watermark appears in the bottom-right of the desktop.
  • EV Code Signing Certificate: For drivers you distribute to end users, you need an Extended Validation (EV) code signing certificate from a Microsoft-approved CA (DigiCert, Sectigo, etc.). These cost ~$400–700/year and require identity verification.
  • WHQL (Windows Hardware Quality Labs): The gold standard — Microsoft tests your driver and adds it to the trusted list. Required for drivers that must install without any security prompts across all Windows configurations. Obtained through the Windows Hardware Dev Center portal.
# Create a self-signed test certificate (development only)
makecert -r -pe -ss PrivateCertStore -n "CN=TestDriverCert" TestCert.cer
certmgr /add TestCert.cer /s /r localMachine root
certmgr /add TestCert.cer /s /r localMachine trustedpublisher

# Sign the .sys file
signtool sign /v /s PrivateCertStore /n "TestDriverCert" \
    /t http://timestamp.digicert.com MinimalDriver.sys

# Verify signature
signtool verify /v /pa MinimalDriver.sys
Warning:Kernel bugs crash the entire operating system. Always develop against a virtual machine with snapshots enabled. Never disable DSE on a production machine — doing so removes a fundamental security boundary and exposes the system to rootkits.
