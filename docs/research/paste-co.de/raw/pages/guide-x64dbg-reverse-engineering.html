Using x64dbg for Reverse Engineering Game Binaries

x64dbg is the de-facto open-source debugger for Windows binary analysis. Built as the modern successor to OllyDbg, it supports both 32-bit (x32dbg) and 64-bit (x64dbg) executables with a rich plugin ecosystem, scriptable automation, and tight integration with disassembly tools like IDA Pro and Ghidra via export formats. This guide focuses on using it specifically for game binary analysis.

Introduction to x64dbg

x64dbg (x64dbg.com) is open source under the GPL license and maintained actively on GitHub. It provides a multi-pane UI with: CPU disassembly view, register window, stack view, memory dump, and a log/command console. Compared to its predecessor OllyDbg, it offers:

  • Native 64-bit support — OllyDbg was 32-bit only. x64dbg ships as paired binaries (x32dbg.exe / x64dbg.exe) and the launcher auto-selects based on target architecture.
  • Plugin API — a rich C++ plugin SDK. Widely-used plugins include ScyllaHide (anti-anti-debug), xAnalyzer (auto-analysis and annotation), and ret-sync (bidirectional sync with IDA/Ghidra).
  • Integrated scripting — a built-in scripting language (x64dbg Script) and Lua support via plugins allow you to automate repetitive analysis tasks.
  • Symbol resolution — downloads PDB symbols from Microsoft Symbol Server and applies them to Windows system DLLs, making call stacks and API calls immediately readable.
  • Conditional and trace breakpoints — break only when a register or memory value matches a condition, or log-and-continue to trace execution without halting.

Attaching vs Opening an Executable

x64dbg offers two entry modes, each suited to different research scenarios:

  • File → Open (F3) — x64dbg launches the target executable itself, breaking at the process entry point (or the TLS callbacks if present). This is the cleanest way to study initialization code, anti-debug routines that run early in startup, or unpacking stubs. The game's anti-cheat may not yet be active at this stage.
  • File → Attach (Alt+A) — attaches to an already-running process. Ideal when you need the game fully loaded and a play session active (so your target data — e.g., a live health value — is present in memory). The debugger interrupts all threads on attach; press Run (F9) to resume.

After attaching, x64dbg populates the Symbols tab with all loaded modules. Expand the game's main module to see exported functions (if any) and referenced imports. Most game binaries strip symbols, so you will see raw addresses — but Windows API imports in the Import Address Table (IAT) remain readable and are extremely useful anchors.

Warning:Attaching a debugger is detectable. Games with active anti-cheat (EAC, BattlEye, Vanguard) instrumentNtQueryInformationProcess, check the BeingDebugged flag in the PEB, and scan for debug registers. Use ScyllaHide or conduct research exclusively in offline / LAN modes.

Setting Breakpoints — Software and Hardware

Breakpoints are the primary mechanism for catching execution at a point of interest. x64dbg supports two fundamentally different kinds:

Software Breakpoints (INT3)

The debugger replaces the first byte of the target instruction with 0xCC (the INT3 opcode). When the CPU executes it, an exception fires and the debugger resumes control. Set one by clicking the left gutter of the CPU view or pressing F2 on a selected instruction. Software BPs are detectable — the game can scan its own code pages for 0xCC bytes.

Hardware Breakpoints (DR0–DR3)

The x86 architecture provides four debug registers (DR0–DR3) that can trigger a debug exception when a specific address is executed, read, or written — without modifying any code bytes. This makes them ideal for catching the exact instruction that reads or writes a game value:

  1. Locate the memory address of the health float (via Cheat Engine, as covered in the ReClass guide).
  2. In x64dbg's Memory Map tab, right-click the address (or use Follow in Dumpfrom the CPU view), then Breakpoint → Hardware, on access (4 bytes).
  3. Return to the game and trigger a health change. The debugger will break at the exact instruction that wrote the new health value — this is the code path you want to analyze.
; Typical result when breaking on health write:
; x64dbg breaks here — call stack will show the combat damage function above

0x7FF63A1B2C40  movss [rcx+88h], xmm0   ; store new health (float) into entity+0x88
                                          ; rcx = PlayerEntity base address
                                          ; xmm0 = computed new health value (e.g., 75.0)
0x7FF63A1B2C48  movss xmm1, [rcx+8Ch]   ; load maxHealth for clamping
0x7FF63A1B2C4D  comiss xmm0, xmm1       ; compare health <= maxHealth
0x7FF63A1B2C50  jbe   short 0x7FF63A1B2C58

The offset 0x88 in the instruction above directly confirms the flHealth offset within the entity structure — exactly what ReClass.NET would show visually.

Reading the Disassembly

Once execution is paused at a breakpoint, the CPU view shows the surrounding disassembly. Recognizing common compiler patterns accelerates analysis significantly.

Function Prologues

MSVC and Clang on x64 Windows always emit a standard prologue. When you see this pattern, you are at the top of a function:

; Standard x64 MSVC function prologue
sub  rsp, 48h           ; reserve shadow space + locals on stack
mov  [rsp+20h], rbx     ; save non-volatile registers
mov  [rsp+28h], rsi
mov  [rsp+30h], rdi
; ... function body follows

Calling Conventions

x64 Windows uses the Microsoft ABI: first four integer/pointer arguments in RCX, RDX, R8, R9; first four float arguments in XMM0–XMM3; additional args on the stack. For C++ member functions, RCX is always this. This means if you break inside a method and see [rcx+88h], you know RCX holds the object pointer and 0x88 is the field offset.

Identifying Loops

; Entity list iteration — common pattern in game update functions
xor  ecx, ecx               ; i = 0
.loop_start:
  cmp  ecx, [rbx+entityCount]; compare i with entity count
  jge  .loop_end             ; if i >= count, exit loop
  movsxd rax, ecx
  lea  rax, [rax+rax*2]      ; rax = i * 3 (stride trick)
  shl  rax, 4                ; rax = i * 48 (entity stride = 0x30)
  add  rax, [rbx+entityBase] ; rax = &entityList[i]
  ; ... process entity at rax
  inc  ecx
  jmp  .loop_start
.loop_end:

Memory Map and Pattern / String Search

x64dbg's Memory Map tab lists every virtual memory region: its base address, size, page protection flags (ERW), memory type (MEM_IMAGE, MEM_PRIVATE), and the module it belongs to. This is essential for:

  • Identifying code vs data sections — MEM_IMAGE + PAGE_EXECUTE_READ regions are code;MEM_PRIVATE + PAGE_READWRITE are heap/stack.
  • String searching — Right-click any module entry → Search for Pattern, or use the command console: findallmem game.exe:, "Player". Games often embed debug strings like"DamagePlayer" or "SetHealth" that directly lead you to the relevant function.
  • Byte pattern (signature) scanning — use the References → Search for dialog or the findall command with a hex pattern to locate a function across updates without knowing its address: findall game.exe:, "F3 0F 11 41 88" (the movss [rcx+88h], xmm0 encoding).

String references are one of the most reliable entry points into unfamiliar code. Once you find the string reference, right-click → Follow in Disassembler → scroll up to see which function uses it and trace its call chain upward.

Scripting with x64dbg Script Language

x64dbg has a built-in scripting language accessible via File → Run Script or the command console. Scripts use a line-oriented syntax with labels, conditionals, and a rich command set. Below is a practical script that automates finding which code path sets the player's health, by setting a hardware breakpoint and logging every write with its context:

// x64dbg Script: trace_health_writes.txt
// Usage: File -> Run Script -> select this file
// Prerequisites: RCX must already point to a known PlayerEntity
//   Set $healthAddr manually before running, or resolve via expression

// ── Step 1: Resolve health field address ─────────────────────────────────
// Assume rcx holds a known player entity base — capture it first via BP
var $entityBase
var $healthAddr

// Read rcx value at current EIP context (after a manual BP on entity ctor)
$entityBase = rcx
$healthAddr = $entityBase + 0x88   // flHealth offset

msg "Health address: {$healthAddr}"

// ── Step 2: Set hardware breakpoint (write, 4 bytes) ─────────────────────
bphws $healthAddr, "w", 4

// ── Step 3: Set a conditional log-and-continue trace ─────────────────────
// bplog logs but does not stop execution — "hit" continues automatically
bplog $healthAddr, "HEALTH WRITE — new value: {[{$healthAddr}]:f}  caller={cip}"

// ── Step 4: Resume execution ──────────────────────────────────────────────
run

// The log tab will accumulate every write to health with the calling address.
// Stop manually (Pause) after triggering several damage events, then review
// the log to find the canonical SetHealth function address.

In the script above, bphws sets a hardware write breakpoint, and bplog configures it as a trace (log-only, no halt). The expression [{$healthAddr}]:f dereferences the health address and formats the result as a 32-bit float. After triggering several damage events in-game, your log will contain lines like:

HEALTH WRITE — new value: 75.000000  caller=7FF63A1B2C40
HEALTH WRITE — new value: 50.000000  caller=7FF63A1B2C40
HEALTH WRITE — new value: 100.000000 caller=7FF63A1B2E90   ; <-- different caller, likely heal

The two distinct callers immediately reveal separate "take damage" and "receive healing" code paths — a level of insight that would take significantly longer to reach manually.

Note:For more complex automation, consider the Lua plugin (LuaScript) or the Python plugin (x64dbgpy), both available in the x64dbg plugin repository. They expose the full debugger API and allow integration with external analysis pipelines.
