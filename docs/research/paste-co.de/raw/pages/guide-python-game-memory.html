Reading Game Memory with Python Using pymem

pymem is a pure-Python library that wraps the Windows ReadProcessMemory and WriteProcessMemory APIs. This guide covers everything from installation to resolving multi-level pointer chains.

1. What Is pymem?

pymem is a Python library that exposes the Windows ReadProcessMemory, WriteProcessMemory, and related memory management APIs through ctypes bindings. It lets you open a handle to any running process, scan its virtual address space, read typed values, and write changes — all from Python without writing a single line of C++.

Its primary use cases in game security research are:

  • Rapid prototyping — Verify that an offset you found in Cheat Engine is correct before hardcoding it into a C++ project. Python's interactive REPL makes this very fast.
  • Simple automation — Build lightweight bots that react to memory-read values (health, position, cooldowns) without a full C++ DLL.
  • Research tooling — Write memory dumpers, structure mappers, and analysis scripts that process game data offline.

Internally, pymem calls OpenProcess with the PROCESS_ALL_ACCESS flag to obtain a handle, then delegates to the Win32 ReadProcessMemory / WriteProcessMemory functions. It also wraps CreateToolhelp32Snapshot for module enumeration, which is how it resolves module base addresses.

2. Installation

pymem is available on PyPI. It requires Python 3.7+ and Windows (it uses Win32 APIs directly and will not work on Linux or macOS). No native compilation is required — it is pure Python.

# Install pymem
pip install pymem

# Optional but recommended for struct unpacking
pip install pywin32

# Verify the install
python -c "import pymem; print(pymem.__version__)"
# Expected: 1.x.x

Run your Python scripts with Administrator privileges. Without elevation, OpenProcess will fail with ERROR_ACCESS_DENIED (5) when trying to attach to most game processes, which run in a higher integrity level or have protected process flags.

Note:Use a virtual environment (python -m venv venv) to isolate pymem from your system Python. This prevents version conflicts when working across multiple research projects.

3. Attaching to a Process by Name

The entry point for any pymem session is the Pymem class. Instantiating it with a process name searches the running process list, finds the PID, and opens a handle automatically.

import pymem
import pymem.process

# Attach by process name (must be running)
pm = pymem.Pymem("game.exe")

# The process ID and handle are now available:
print(f"PID:    {pm.process_id}")
print(f"Handle: {pm.process_handle}")

# Get the base address of the main module (game.exe itself):
base = pymem.process.module_from_name(pm.process_handle, "game.exe").lpBaseOfDll
print(f"Base address: {hex(base)}")

# You can also get any loaded module's base:
engine_base = pymem.process.module_from_name(pm.process_handle, "engine.dll").lpBaseOfDll
print(f"engine.dll base: {hex(engine_base)}")

If the process is not running, pymem raises pymem.exception.ProcessNotFound. Wrap the constructor in a try/except during development to handle this gracefully:

import pymem
from pymem.exception import ProcessNotFound

try:
    pm = pymem.Pymem("game.exe")
except ProcessNotFound:
    print("game.exe is not running. Launch the game first.")
    raise SystemExit(1)

4. Reading Basic Types

pymem provides convenience methods for reading common primitive types directly from a memory address. Under the hood each of these calls ReadProcessMemory and unpacks the raw bytes using Python's struct module.

import pymem
import struct

pm = pymem.Pymem("game.exe")

# --- Reading integers ---
# Read a 4-byte signed integer (int32) from an absolute address
health_addr = 0x1A2B3C40
health = pm.read_int(health_addr)
print(f"Health: {health}")

# Read an 8-byte integer (int64 / QWORD)
score = pm.read_longlong(0x1A2B3C50)

# Read a 4-byte unsigned integer (DWORD)
flags = pm.read_uint(0x1A2B3C60)

# --- Reading floats ---
# Read a single-precision 4-byte float (the most common in games)
speed = pm.read_float(0x1A2B3C70)
print(f"Speed: {speed:.2f}")

# --- Reading booleans ---
# Games typically store bools as a single byte (0 or 1)
is_grounded_byte = pm.read_bytes(0x1A2B3C80, 1)
is_grounded = bool(is_grounded_byte[0])

# --- Reading a Vec3 (3D position vector) ---
# A Vec3 is 3 consecutive floats: X at addr, Y at addr+4, Z at addr+8
def read_vec3(pm: pymem.Pymem, address: int) -> tuple[float, float, float]:
    raw = pm.read_bytes(address, 12)  # 3 floats * 4 bytes each = 12 bytes
    x, y, z = struct.unpack("fff", raw)
    return (x, y, z)

pos_addr = 0x1A2B3C90
pos = read_vec3(pm, pos_addr)
print(f"Player position: X={pos[0]:.2f}, Y={pos[1]:.2f}, Z={pos[2]:.2f}")

The full list of pymem read methods includes: read_int, read_uint, read_short, read_ushort, read_long, read_ulong, read_longlong, read_ulonglong, read_float, read_double, read_bool, read_char, read_string, and read_bytes. For any type not directly supported, use read_bytes(addr, n) and unpack manually with struct.unpack.

5. Pointer Chain Resolution

Games allocate most of their game-state objects on the heap at addresses that change every time the process starts (due to ASLR and heap randomization). A pointer chain is a sequence of memory reads starting from a stable base address (usually a static offset from the module base) that navigates through a series of pointers — each read gives you the address for the next step — until you reach the final value.

Cheat Engine's pointer scanner finds these chains for you. The chain is typically represented as: [[[base + 0x1A0] + 0x48] + 0x18] + 0xC — meaning a 4-step chain with 3 dereferences and a final offset.

import pymem
import pymem.process

def resolve_pointer_chain(
    pm: pymem.Pymem,
    base_address: int,
    offsets: list[int]
) -> int:
    """
    Resolve a multi-level pointer chain.

    Args:
        pm:           Pymem instance attached to the target process.
        base_address: The starting static address (e.g., module base + static offset).
        offsets:      List of offsets to dereference in order.
                      The last offset is added but NOT dereferenced —
                      it gives the final address of the target value.

    Returns:
        The final resolved address of the target value.

    Example chain from Cheat Engine:
        [[[game.exe + 0x01A2B3C0] + 0x48] + 0x18] + 0x0C
        base_address = module_base + 0x01A2B3C0
        offsets      = [0x48, 0x18, 0x0C]
    """
    addr = pm.read_longlong(base_address)   # First dereference from static base
    for offset in offsets[:-1]:             # All offsets except the last
        addr = pm.read_longlong(addr + offset)
    return addr + offsets[-1]              # Final offset — the value's address


# Example usage:
pm = pymem.Pymem("game.exe")
module_base = pymem.process.module_from_name(
    pm.process_handle, "game.exe"
).lpBaseOfDll

# Pointer chain found with Cheat Engine:
# game.exe + 0x01A2B3C0 → +0x48 → +0x18 → +0x0C  (target: player health, int32)
STATIC_OFFSET = 0x01A2B3C0
OFFSETS       = [0x48, 0x18, 0x0C]

try:
    health_addr = resolve_pointer_chain(
        pm,
        module_base + STATIC_OFFSET,
        OFFSETS
    )
    health = pm.read_int(health_addr)
    print(f"Player health: {health}")
except Exception as e:
    # A read_longlong will throw if any intermediate pointer is NULL or invalid
    print(f"Pointer chain broken — game may not be in a valid state: {e}")


# --- Writing through the pointer chain ---
def write_via_chain(pm, base_address, offsets, value_writer, value):
    addr = resolve_pointer_chain(pm, base_address, offsets)
    value_writer(addr, value)

# Set health to 100:
write_via_chain(pm, module_base + STATIC_OFFSET, OFFSETS, pm.write_int, 100)
Note:On a 64-bit process, always use read_longlong (8 bytes) to dereference pointers — not read_int (4 bytes). Using the wrong size will truncate the pointer and produce an invalid address. On legacy 32-bit games, use read_uint (4 bytes) for pointer reads.

6. Limitations vs. C++

pymem is a great prototyping tool but has fundamental limitations compared to a proper C++ DLL injected into the game process. Understanding these tradeoffs helps you decide when Python is sufficient and when to graduate to C++.

  • Performance: Every ReadProcessMemory call crosses a process boundary — it is a kernel transition. Python adds interpreter overhead on top of this. A tight Python loop reading memory 60 times/second will consume noticeably more CPU than an equivalent C++ DLL running in-process, where a memory read is a single pointer dereference with no syscall overhead.
  • Anti-cheat detection: External memory reading (a separate .exe or script calling ReadProcessMemory on the game) is one of the most-watched patterns by kernel-level anti-cheat software. A Python process with PROCESS_ALL_ACCESS on a game handle is trivially detectable. C++ code injected as a DLL runs inside the game's address space and has a smaller detection surface — though it is by no means undetectable.
  • No kernel access: pymem operates entirely in user mode. It cannot hook kernel callbacks, read kernel-mode data structures (EPROCESS, KTHREAD), manipulate driver objects, or bypass kernel-mode anti-cheat protections that operate at ring 0. Any research involving kernel-level techniques requires a Windows driver (WDM/WDF) written in C.
  • No code injection: pymem can write bytes to memory, but it cannot easily allocate remote executable memory, write shellcode, or call game functions — tasks that require VirtualAllocEx + WriteProcessMemory + CreateRemoteThread or equivalent techniques, which are much simpler to orchestrate from C++.
  • Windows-only: The underlying Win32 APIs are Windows-specific. pymem will not run on Linux (Proton/Wine environments present a different memory API surface) or macOS.
When to use pymem vs. C++:Use pymem when you are exploring an unknown game and validating offsets, or building a one-off research script. Switch to C++ when you need in-process speed, code hooking (trampolines, vtable patches), or anything requiring more than basic memory read/write from outside the process.
