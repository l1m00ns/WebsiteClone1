Pattern Scanning — Finding Functions in Game Memory by Byte Signature

Pattern scanning (also called signature scanning or AOB scanning — Array of Bytes) is the technique of locating code or data in a process's memory by searching for a known sequence of bytes rather than relying on a fixed address. It is a cornerstone of game modding and reverse engineering because it survives minor game updates where only offsets shift.

What Is Pattern Scanning and Why Use It?

When you reverse engineer a game and find the function that applies damage, you could hardcode its address — say 0x140A3F220. But the next game update recompiles the binary. New functions are added, the compiler reorders code, and your hardcoded address now points into the middle of a completely different function. Your mod crashes.

The insight behind pattern scanning is that while addresses change between updates, the compiled machine code of a specific function tends to be much more stable. A function's prologue — the first 15–30 bytes of its assembly — is often identical across minor patches because the compiler generates the same code from the same source. Instead of storing 0x140A3F220, you store the byte sequence 48 89 5C 24 08 57 48 83 EC 30 48 8B D9 and scan for it at runtime.

Pattern scanning is used extensively in:

  • Game trainers and mods — locating game logic without source access
  • Anti-cheat bypass research — finding integrity-checking routines
  • Instrumentation and profiling — hooking functions dynamically
  • Malware analysis — identifying code patterns across obfuscated samples

Generating a Pattern in IDA Pro and Ghidra

The goal is to find a sequence of bytes at the start (or a distinctive location) of your target function that is unique in the entire binary and unlikely to change across updates.

In IDA Pro:

  1. Navigate to the function in the disassembly view. Press F2 to enter hex view, or use View → Open Subviews → Hex Dump.
  2. Read the raw bytes of the function's first 10–20 instructions. Right-click the function start in the disassembly → Search → Text... to verify the sequence appears only once in the entire binary.
  3. Alternatively, install the findcrypt or sigmaker IDA plugin. Sigmaker automatically generates a minimal unique signature for the selected address, outputting it in CE-style (?? ?? 48 89) or code-style byte array format.

In Ghidra:

  1. Open the function in the Listing view. The byte values are shown in the second column to the left of the mnemonics.
  2. Use Search → Memory... (S) to enter your candidate byte sequence and verify it appears exactly once. Use \x?? as a wildcard.
  3. The community plugin SigMaker-Ghidra (available on GitHub) automates the process of growing a signature byte-by-byte until it is unique.

Wildcards — The ? Byte

Not all bytes in a pattern can be matched exactly. Some bytes encode relative addresses or absolute addresses that the linker fills in and that change every build. The canonical example is a relative CALL or JMP instruction:

  • E8 xx xx xx xx — CALL rel32. The 4 bytes after E8 are a signed 32-bit offset from the next instruction to the target. If any code between this call site and its target is added or removed, this offset changes. Wildcard all 4 bytes: E8 ?? ?? ?? ??.
  • 48 8D 05 xx xx xx xx — LEA rax, [rip + rel32]. RIP-relative data references similarly encode runtime-dependent offsets. Wildcard the 4-byte displacement.
  • FF 15 xx xx xx xx — CALL QWORD PTR [rip + rel32]. Indirect calls through the import table. Wildcard the 4 displacement bytes.

Instructions that are safe to match exactly include register-to-register operations, immediate values that are part of the algorithm logic (not addresses), and stack frame setup sequences. A good rule of thumb: if the byte sequence encodes an address, wildcard it; if it encodes logic, keep it.

Tip:Aim for patterns between 12 and 25 bytes. Shorter patterns risk false positives; longer patterns become brittle across updates (more bytes = more chances for the compiler to change something). Cross-reference your pattern against two or three game versions to verify stability before shipping.

Implementing a Pattern Scanner in C++

The scanner below operates on memory already mapped into the current process (e.g., an injected DLL scanning the host game). It parses an IDA-style pattern string ("48 89 5C ?? ?? 57") into a byte/mask pair, then iterates over executable memory regions using VirtualQuery.

// pattern_scanner.hpp
#pragma once
#include <Windows.h>
#include <vector>
#include <string>
#include <sstream>
#include <cstdint>
#include <optional>

struct PatternByte {
    uint8_t  value;
    bool     isWildcard;
};

// Parse "48 89 5C ?? 08 57" into a vector of PatternByte
inline std::vector<PatternByte> ParsePattern(const std::string& pattern)
{
    std::vector<PatternByte> result;
    std::istringstream ss(pattern);
    std::string token;

    while (ss >> token) {
        PatternByte pb{};
        if (token == "?" || token == "??") {
            pb.isWildcard = true;
            pb.value      = 0x00;
        } else {
            pb.isWildcard = false;
            pb.value      = static_cast<uint8_t>(std::stoul(token, nullptr, 16));
        }
        result.push_back(pb);
    }
    return result;
}

// Compare bytes at 'data' against 'pattern', respecting wildcards
inline bool MatchPattern(const uint8_t* data,
                          const std::vector<PatternByte>& pattern)
{
    for (size_t i = 0; i < pattern.size(); ++i) {
        if (!pattern[i].isWildcard && data[i] != pattern[i].value)
            return false;
    }
    return true;
}

// Scan a single contiguous region [base, base+size) for the pattern
inline std::optional<uintptr_t> ScanRegion(const uint8_t* base,
                                             size_t regionSize,
                                             const std::vector<PatternByte>& pattern)
{
    if (pattern.empty() || regionSize < pattern.size())
        return std::nullopt;

    const size_t scanEnd = regionSize - pattern.size();
    for (size_t offset = 0; offset <= scanEnd; ++offset) {
        if (MatchPattern(base + offset, pattern))
            return reinterpret_cast<uintptr_t>(base + offset);
    }
    return std::nullopt;
}

// Scan all committed, executable memory regions of the current process
// for the given IDA-style pattern string. Returns the first match.
inline std::optional<uintptr_t> PatternScan(const std::string& patternStr)
{
    auto pattern = ParsePattern(patternStr);
    if (pattern.empty())
        return std::nullopt;

    MEMORY_BASIC_INFORMATION mbi{};
    uintptr_t address = 0;

    while (VirtualQuery(reinterpret_cast<LPCVOID>(address), &mbi, sizeof(mbi))
           == sizeof(mbi))
    {
        // Only scan committed, executable regions (skip guard pages, no-access)
        bool isCommitted   = (mbi.State   == MEM_COMMIT);
        bool isExecutable  = (mbi.Protect & (PAGE_EXECUTE |
                                              PAGE_EXECUTE_READ |
                                              PAGE_EXECUTE_READWRITE |
                                              PAGE_EXECUTE_WRITECOPY));
        bool notGuard      = !(mbi.Protect & PAGE_GUARD);

        if (isCommitted && isExecutable && notGuard) {
            auto match = ScanRegion(
                reinterpret_cast<const uint8_t*>(mbi.BaseAddress),
                mbi.RegionSize,
                pattern
            );
            if (match.has_value())
                return match;
        }

        // Advance to the next region; guard against overflow
        uintptr_t next = reinterpret_cast<uintptr_t>(mbi.BaseAddress) + mbi.RegionSize;
        if (next <= address) break;  // wrapped around
        address = next;
    }

    return std::nullopt;
}

The scanner runs in O(n·m) time where n is the total committed executable bytes and m is pattern length. For a 100 MB game binary this takes roughly 50–200ms on modern hardware — acceptable for one-time initialization but too slow to call per-frame.

Using VirtualQuery to Enumerate Memory Regions

VirtualQuery (or VirtualQueryEx for external processes) fills a MEMORY_BASIC_INFORMATION structure describing the region that starts at or contains the queried address. Key fields:

typedef struct _MEMORY_BASIC_INFORMATION {
    PVOID  BaseAddress;       // start of this region
    PVOID  AllocationBase;    // base of the VirtualAlloc that created it
    DWORD  AllocationProtect; // protection at allocation time
    SIZE_T RegionSize;        // byte size of this region (contiguous same-attribute pages)
    DWORD  State;             // MEM_COMMIT | MEM_FREE | MEM_RESERVE
    DWORD  Protect;           // current protection flags (PAGE_EXECUTE_READ, etc.)
    DWORD  Type;              // MEM_IMAGE | MEM_MAPPED | MEM_PRIVATE
} MEMORY_BASIC_INFORMATION;

// To restrict scanning to a specific module only (much faster):
// 1. Get module base: GetModuleHandleA("game.exe")
// 2. Read PE header to get SizeOfImage
// 3. Call ScanRegion() on [moduleBase, moduleBase + SizeOfImage]

HMODULE hMod = GetModuleHandleA(nullptr); // nullptr = main EXE
MODULEINFO mi{};
GetModuleInformation(GetCurrentProcess(), hMod, &mi, sizeof(mi));
// mi.lpBaseOfDll = base address
// mi.SizeOfImage = total mapped size

Restricting the scan to a known module's image region (Type == MEM_IMAGE) dramatically reduces scan time and false positives, since you are only searching compiled code pages rather than heap allocations or stack memory. For a 64 MB game EXE, the scan typically completes in under 10ms.

Caching Patterns and Handling Update Breakage

Scanning on every launch adds startup latency. A simple caching strategy stores the resolved address alongside a game build identifier (e.g., a hash of the EXE or the PE TimeDateStamp field) in a local config file. On next launch, if the build ID matches, use the cached offset directly; otherwise re-scan and update the cache.

// cache.hpp  — simplified offset cache
#pragma once
#include <Windows.h>
#include <fstream>
#include <unordered_map>
#include <string>

// Read PE TimeDateStamp as a simple build fingerprint
inline uint32_t GetModuleTimestamp(HMODULE hMod)
{
    auto* dosHdr = reinterpret_cast<IMAGE_DOS_HEADER*>(hMod);
    auto* ntHdr  = reinterpret_cast<IMAGE_NT_HEADERS*>(
        reinterpret_cast<uint8_t*>(hMod) + dosHdr->e_lfanew);
    return ntHdr->FileHeader.TimeDateStamp;
}

struct OffsetCache {
    uint32_t                           buildStamp = 0;
    std::unordered_map<std::string, uintptr_t> offsets;

    void Load(const std::string& path) { /* read JSON/INI */ }
    void Save(const std::string& path) { /* write JSON/INI */ }

    uintptr_t Resolve(const std::string& name,
                      const std::string& pattern,
                      HMODULE            hMod)
    {
        uint32_t stamp = GetModuleTimestamp(hMod);
        if (buildStamp != stamp) {
            offsets.clear();       // stale cache — invalidate everything
            buildStamp = stamp;
        }

        auto it = offsets.find(name);
        if (it != offsets.end())
            return it->second;     // cache hit

        // Cache miss — scan
        auto base   = reinterpret_cast<uintptr_t>(hMod);
        auto result = PatternScan(pattern);      // scoped to module for speed
        if (!result) return 0;

        uintptr_t offset = *result - base;       // store as relative offset
        offsets[name]    = offset;
        return *result;
    }
};

When a game update does break a pattern, the fallback strategy is to have multiple candidate patterns for the same target — ordered from most to least specific — and try them in sequence. Automated CI pipelines in larger modding communities download new game builds, run the pattern list, and report which signatures need updating before the community is even aware the game patched.

Advanced Technique:Instead of matching at the function entry point, match at a distinctive instruction deep inside the function body, then walk backward to the nearest CC CC CC (INT3 padding) or 90 90 90 (NOP padding) alignment sequence to find the true function start. This works even when the prologue changes but the body is stable.
