Finding Game Offsets with ReClass.NET

ReClass.NET is an indispensable tool for game memory work. It lets you attach to a running process, inspect raw memory, and visually reconstruct the C++ class and struct layouts that a game uses internally — without access to source code. This guide walks through the full workflow from locating a value to exporting stable offset constants.

What Are Offsets and Why Do They Matter?

When a game runs, it allocates objects in memory — player entities, physics bodies, UI state, etc. These objects are C++ classes or structs laid out contiguously in RAM. An offset is the byte distance from the start of a structure to a particular member field. For example, if a PlayerEntity struct starts at address 0x12340000 and the health field is 0x100 bytes into the struct, then the absolute address of health is 0x12340100.

The problem is that the struct's base address changes every time the game restarts (ASLR — Address Space Layout Randomization). What stays stable across sessions are:

  • Module base offsets — the offset of a global variable from the start of the game's loaded module (.exe or .dll). The module base address varies, but the offset within it is fixed at compile time.
  • Pointer chains (multi-level pointers) — a static global pointer stored at a fixed module offset that points to a heap-allocated object, which in turn contains another pointer, and so on. Tools like Cheat Engine call these "pointer scans."
  • Member offsets within a struct — the byte distance from the struct's base to each field, which is determined at compile time and never changes between game builds of the same version.

Understanding this distinction — between absolute addresses (unstable) and relative offsets (stable) — is the foundation of any memory-based workflow.

Setting Up ReClass.NET

ReClass.NET is open source and maintained on GitHub under the ReClassNET/ReClass.NET repository. Download the latest release ZIP, extract it, and run ReClass.NET.exe as Administrator — elevated privileges are required to open handles to other processes with PROCESS_VM_READ access rights.

  1. Launch your target game and let it reach a gameplay state where the data you want to inspect is live in memory.
  2. In ReClass.NET, go to File → Open Process (or press Ctrl+O). A process list dialog appears. Select your game's process — typically the main .exe name.
  3. A new node view opens, starting at address 0x0000000000000000. This is a blank class that you will populate with memory reads once you have a target address.
  4. Optionally configure the "Settings" to show the module name alongside each address, which makes it easier to calculate stable module-relative offsets.
Note:Some anti-cheat protected games will terminate or flag the process if ReClass.NET attaches. Always conduct memory research in offline/single-player modes or on isolated research environments. Never attach to live competitive multiplayer sessions.

Scanning with Cheat Engine First

ReClass.NET is a structural inspector, not a scanner. You first need to know the address of something interesting before you can explore the surrounding memory layout. Cheat Engine excels at this initial discovery phase.

  1. Open Cheat Engine, attach it to the game process, and perform a scan for your target value — for example, current health as a 4-byte float. Take damage, scan for the new value. Repeat until you narrow down to one or a handful of addresses.
  2. Right-click a promising address in Cheat Engine and choose Find out what writes to this address. Apply damage again. The debugger window will show the instruction that wrote to the health field — this confirms you have the right address.
  3. Copy the address (e.g., 0x1FE3A2B4C0). Switch to ReClass.NET.
  4. In ReClass.NET, right-click the root class node and choose Change Address. Paste the address. ReClass will immediately begin reading 512 bytes of memory starting from that address and display them as a grid of nodes.

At this point you are looking at the raw bytes of whatever object lives at that address. The goal is to figure out whether you're looking at the field itself or the object that contains the field. If the address is your health float directly, you likely want to walk the memory backwards to find the object's base — subtract small amounts (try 0x10, 0x20, 0x40, etc.) and look for a vtable pointer (a pointer-sized value that points into the game's code section) at offset 0x00, which is the hallmark of a C++ polymorphic object.

Reading the Class / Struct Layout

Once you have the object base loaded in ReClass.NET, each row in the node grid represents one node (field). By default all nodes render as Hex 8 (8 bytes of raw hex). Your job is to right-click each node and assign it the correct type. Common types you will encounter:

  • Pointer (Ptr64 / Ptr32) — a value that is itself an address pointing elsewhere. If you see a value like 0x00007FF6AABBCCDD in a 64-bit process, it's almost certainly a pointer. You can "follow" it by right-clicking → Create Class at Pointer.
  • Float32 — health, speed, position components, timers. Values between roughly ±100,000 that change smoothly.
  • Int32 / UInt32 — ammo counts, enum states, flags bitmasks, item IDs.
  • Vector3 (Vec3) — three consecutive float32 values representing X, Y, Z. ReClass.NET has a built-in Vec3 node type. World-position fields are almost always Vec3 at a recognizable offset like 0x28, 0x38, or 0x78.
  • Bool / Byte — single-byte flags (is_dead, is_crouching, team_id).

Double-click a node to rename it. Build up your class definition field by field. As you rename and type nodes, ReClass.NET automatically shows the offset of each field in the leftmost column — this is the offset you will export to your code. For example, after analysis you might document:

// Reconstructed layout of PlayerEntity (0x500 bytes total)
// Offset   Size  Name
// 0x0000   8     vftable (pointer to vtable)
// 0x0008   8     pEntityList (pointer)
// 0x0028   12    vecOrigin (Vector3 - world position X,Y,Z)
// 0x0034   12    vecVelocity (Vector3)
// 0x0088   4     flHealth (float)
// 0x008C   4     flMaxHealth (float)
// 0x0090   4     iTeamNum (int32)
// 0x0094   1     bAlive (bool)
// 0x00A0   4     iAmmoCount (int32)
// 0x00C0   8     pWeapon (pointer to WeaponEntity)

Exporting Offsets to C++ Code

Once you have documented your offsets, you express them in C++ as typed constants and use pointer arithmetic withReadProcessMemory (for external tools) or direct dereferencing (for internal DLLs). Below is a complete example of an external reader using the offsets discovered above.

#include <Windows.h>
#include <cstdint>
#include <cstdio>

// ─── Offsets (discovered via ReClass.NET) ──────────────────────────────────
namespace offsets {
    // From module base to the static pointer that holds the entity list root
    constexpr uintptr_t entityList     = 0x01A2B3C0; // example — find via pointer scan

    // From a PlayerEntity base address to each member field
    constexpr uintptr_t vecOrigin      = 0x0028;
    constexpr uintptr_t vecVelocity    = 0x0034;
    constexpr uintptr_t flHealth       = 0x0088;
    constexpr uintptr_t flMaxHealth    = 0x008C;
    constexpr uintptr_t iTeamNum       = 0x0090;
    constexpr uintptr_t bAlive         = 0x0094;
}

// ─── Helpers ───────────────────────────────────────────────────────────────
struct Vec3 { float x, y, z; };

// Read T bytes from a remote process at 'address'
template <typename T>
T RPM(HANDLE hProc, uintptr_t address) {
    T value{};
    ReadProcessMemory(hProc, reinterpret_cast<LPCVOID>(address),
                      &value, sizeof(T), nullptr);
    return value;
}

// Dereference a pointer chain:
//   base + offset[0] → ptr1
//   ptr1 + offset[1] → ptr2  ... → final address
uintptr_t ResolvePointerChain(HANDLE hProc, uintptr_t base,
                               const std::initializer_list<uintptr_t>& offsets) {
    uintptr_t addr = base;
    for (auto off : offsets) {
        addr = RPM<uintptr_t>(hProc, addr) + off;
    }
    return addr;
}

// ─── Main ──────────────────────────────────────────────────────────────────
int main() {
    // Attach to game (see module base guide for GetModuleBaseAddress)
    HANDLE hProc = OpenProcess(PROCESS_VM_READ, FALSE, /* pid */ 12345);
    uintptr_t moduleBase = 0x7FF600000000; // obtained from TH32 snapshot

    // Resolve the local player entity pointer
    uintptr_t localPlayer = ResolvePointerChain(hProc, moduleBase,
        { offsets::entityList, 0x0, 0x58 }); // example multi-level chain

    if (!localPlayer) {
        puts("Failed to resolve local player pointer.");
        return 1;
    }

    // Read individual fields
    Vec3  origin    = RPM<Vec3> (hProc, localPlayer + offsets::vecOrigin);
    float health    = RPM<float>(hProc, localPlayer + offsets::flHealth);
    float maxHealth = RPM<float>(hProc, localPlayer + offsets::flMaxHealth);
    int   team      = RPM<int>  (hProc, localPlayer + offsets::iTeamNum);
    bool  alive     = RPM<bool> (hProc, localPlayer + offsets::bAlive);

    printf("Position : (%.1f, %.1f, %.1f)\n", origin.x, origin.y, origin.z);
    printf("Health   : %.0f / %.0f\n", health, maxHealth);
    printf("Team     : %d  |  Alive: %s\n", team, alive ? "yes" : "no");

    CloseHandle(hProc);
    return 0;
}

Pointer Scanning for Stable Multi-Level Pointers

A single absolute address for a heap-allocated object changes every session. To get a persistent path to your data, you need a pointer chain that starts at a statically addressed location (within the game module) and chains through heap pointers via known offsets. Cheat Engine's Pointer Scanner automates this discovery.

  1. With the target address still highlighted in Cheat Engine, go to Memory View → Tools → Pointer Scanner → Scan for pointers pointing to this address.
  2. Configure: Max level = 4–5, Max offset per level = 0x800 (increase for deeper chains). Check "Only find paths with static base" — this forces the first pointer in the chain to be within the loaded module image, giving you a stable starting point.
  3. Save the results. Restart the game. Re-scan the pointer list against the new address of the same value. Surviving results are stable pointer chains.
  4. A stable result looks like: game.exe+0x01A2B3C0 → +0x58 → +0x10 → +0x88. This means read a pointer at moduleBase + 0x01A2B3C0, add 0x58, follow that pointer, add 0x10, follow again, and the health float lives at the final address plus 0x88.

In ReClass.NET, you can visualize the same chain by following pointers level by level — each "Create Class at Pointer" operation drills one level deeper. Once the full chain is mapped, export the offset constants and encode them as an initializer list in the ResolvePointerChain function shown above.

Note:Offsets are version-specific. When a game updates, structures may be reordered or padded differently. Always re-verify offsets after patches by repeating the scan + ReClass inspection workflow. Automated offset scanners (pattern scanning for known byte sequences in the binary) can help re-find offsets quickly after updates.
