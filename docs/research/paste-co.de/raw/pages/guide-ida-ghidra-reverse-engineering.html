IDA Pro and Ghidra for Game Reverse Engineering — Getting Started

Static disassemblers and decompilers are the most powerful tools in a reverse engineer's arsenal. This guide covers loading a game binary, reading decompiler output, finding structures, and building an annotated knowledge base of a target binary.

1. IDA Pro vs. Ghidra — Choosing Your Tool

Both IDA Pro and Ghidra are production-grade disassemblers and decompilers capable of analyzing stripped 64-bit PE binaries (the format used by most Windows games). The choice between them comes down to cost, ecosystem, and personal workflow.

IDA Pro (Hex-Rays) is the long-standing industry standard. Its disassembler is widely regarded as the most accurate available, and the Hex-Rays Decompiler plugin produces cleaner C pseudo-code than most alternatives. IDA's type reconstruction, structure layout editor, and scripting API (IDAPython) are mature and well-documented. The tradeoff is cost — a perpetual license for IDA Pro with the Hex-Rays x64 decompiler exceeds $3,000 USD. There is a free tier called IDA Free (limited to 32-bit x86 analysis) and cloud decompilation via Dogbolt / hex-rays.com for quick one-off analysis.

Ghidra was developed by the NSA's Research Directorate and released as open source in 2019. It is completely free, supports a wide range of processor architectures (x86-16/32/64, ARM, MIPS, PowerPC, and dozens more), and includes a built-in decompiler that produces C pseudo-code of comparable quality to Hex-Rays for most game analysis tasks. Its scripting API (Ghidra Script, Java or Python via Jython) and plugin ecosystem have grown substantially since release. For the purposes of game security research, Ghidra is an excellent and sufficient choice.

  • Cost: IDA Pro — paid ($3k+) | Ghidra — free
  • Decompiler quality: IDA Hex-Rays — excellent | Ghidra — very good, occasional artifacts
  • Scripting: IDA — IDAPython (mature) | Ghidra — Java / Jython / GhidraScript
  • Plugin ecosystem: IDA — large, commercial plugins available | Ghidra — growing, all open source
  • PDB support: Both support importing Microsoft PDB files for symbol-assisted analysis

2. Loading a Game Binary in Ghidra

Ghidra requires Java 17 or later. Download from ghidra-sre.org, extract the archive, and run ghidraRun.bat (Windows) or ghidraRun (Linux/macOS). No installation is required — Ghidra is fully portable.

  1. Create a project: File → New Project → Non-Shared Project. Give it a name matching the game. Projects store all your analysis, annotations, and renamed symbols — treat them as the primary output of your research.
  2. Import the binary: File → Import File → select the game's main .exe. Ghidra will auto-detect the format. For most modern Windows games you will see:
    Format:    Portable Executable (PE)
Language:  x86:LE:64:default:windows   ← 64-bit x86, little-endian
Compiler:  windows                     ← MSVC detection
  3. Load PDB if available: If the game ships with a PDB file (some older or indie games do), Ghidra will offer to apply it. This populates function names, type information, and global variable names, saving enormous amounts of manual work. Accept this — it is one of the highest-leverage actions available.
  4. Run auto-analysis: After import, Ghidra prompts to analyze. Accept the defaults. The analysis phase disassembles the entire binary, identifies function boundaries, recovers call graphs, and applies FLIRT-style signature matching to identify standard library functions (CRT, STL, etc.). This takes 1–20 minutes depending on binary size.
Note:Never analyze the actual game binary that the game runs from. Copy the .exe and any associated .dll files you want to analyze to your research directory first. Ghidra may lock the file, and you want the original untouched for comparison across patches.

3. The Decompiler View — Reading C Pseudo-code

Click any function in the Symbol Tree or double-click an address in the Listing (disassembly) view. The Decompiler window on the right shows Ghidra's C pseudo-code reconstruction. This is not the original source code — it is a best-effort reconstruction from machine instructions, and it contains artifacts.

Here is a simplified example of what Ghidra's decompiler output typically looks like for a stripped player update function before any annotation:

// Ghidra decompiler output — BEFORE annotation
// Function: FUN_140123ab0  (auto-generated name)

void FUN_140123ab0(longlong param_1, float param_2)
{
  float fVar1;
  float fVar2;
  longlong *plVar3;

  if (*(int *)(param_1 + 0x18) != 0) {        // health check
    fVar1 = *(float *)(param_1 + 0x44);       // current X velocity
    fVar2 = *(float *)(param_1 + 0x48);       // current Y velocity
    fVar1 = fVar1 + *(float *)(param_1 + 0x8c) * param_2;  // integrate X
    fVar2 = fVar2 + *(float *)(param_1 + 0x94) * param_2;  // integrate Y
    *(float *)(param_1 + 0x44) = fVar1;
    *(float *)(param_1 + 0x48) = fVar2;
    *(float *)(param_1 + 0x3c) = *(float *)(param_1 + 0x3c) + fVar1 * param_2;
    *(float *)(param_1 + 0x40) = *(float *)(param_1 + 0x40) + fVar2 * param_2;
    plVar3 = *(longlong **)(param_1 + 0x100);  // pointer to another object
    if (plVar3 != (longlong *)0x0) {
      FUN_14009af20(plVar3, param_1);           // call on child object
    }
  }
  return;
}

Common decompiler artifacts to be aware of:

  • Raw offset access like *(float *)(param_1 + 0x44) — this means the compiler optimized away a named struct member. The offset 0x44 is the byte offset into a class/struct. Collecting these offsets is how you reconstruct class layouts.
  • Auto-generated names like FUN_140123ab0, param_1, fVar1 — rename these as you understand them. Use Ghidra's L key shortcut to rename any symbol.
  • Inlined functions — Small functions get inlined by the compiler and appear as inline code in the caller's decompilation. They won't have separate function entries in the Symbol Tree.
  • Type confusion — Ghidra may represent a float field as an int or vice versa if it can't determine the type from context alone. Right-click a variable and use Retype Variable to correct this.

4. Finding Interesting Functions

A stripped game binary contains thousands of unnamed functions. The challenge is navigating to the ones relevant to your research. The following techniques are the most effective entry points:

String reference search: Games frequently log errors or debug messages as string literals embedded in the binary. These strings survive stripping. Search → For Strings, filter by a known term (e.g., "PlayerController", "health", "damage", "spawn"), then use cross-references (right-click → References → Find References) to navigate to the code that uses each string. The surrounding code is often exactly the function you want.

# Ghidra Script example: Find all functions that reference a specific string
# Run via: Window → Script Manager → New Script → Python

from ghidra.program.model.symbol import SymbolType

target_string = "PlayerTakeDamage"

# Find the string in the defined data
data_iter = currentProgram.getListing().getDefinedData(True)
for data in data_iter:
    if data.hasStringValue() and target_string in str(data.getValue()):
        addr = data.getAddress()
        print(f"Found string at: {addr}")
        # Get all code references to this string address
        refs = getReferencesTo(addr)
        for ref in refs:
            fn = getFunctionContaining(ref.getFromAddress())
            if fn:
                print(f"  Referenced in function: {fn.getName()} @ {fn.getEntryPoint()}")

Import table analysis: Look at the binary's imports (Window → Symbol Tree → Imports). Calls to VirtualAlloc, custom memory allocators, or STL container functions give clues about memory management patterns. Functions importing GetAsyncKeyState or XInputGetState lead to input handling.

Function size heuristics: Sort the function list by size (Window → Symbol Tree → Functions, right-click header → Column Settings → add Size). Very large functions (2000+ instructions) are often update loops, game state managers, or physics solvers — prime targets for reverse engineering.

5. Identifying Entity and Player Structures

In C++ games, player and entity data is stored in class instances (objects). The decompiler represents field accesses as *(type *)(param + offset) patterns. When you see the same parameter accessed repeatedly at different offsets across many functions, that parameter is almost certainly a pointer to a key class instance (e.g., CPlayer, EntityBase, ACharacter).

The workflow for reconstructing a structure:

  1. Find a function that clearly operates on a player object (e.g., a damage function found via string search for "damage" or "health").
  2. Note every offset accessed on the first parameter. Each unique offset is a struct field. Common patterns: floats at small offsets (4, 8, 12) are often position/velocity; small integers at mid-range offsets (0x10–0x30) are IDs or flags; floats in the 0x3C–0x50 range in update functions are often health/mana values.
  3. Use Ghidra's Data Type Manager (Window → Data Type Manager) to create a new Structure type. Add fields at each discovered offset with their inferred types.
  4. Retype param_1 in the function to your new structure pointer type (right-click → Retype Variable → select your struct). Ghidra will immediately update all field accesses in the decompiler to use named members.
// Before retyping param_1:
if (*(int *)(param_1 + 0x18) != 0) {
  fVar1 = *(float *)(param_1 + 0x3c);

// After creating struct CPlayer and retyping:
if (player->isAlive != 0) {
  fVar1 = player->health;

Cross-reference the structure pointer globally — right-click the parameter → References → Find References to Symbol. Ghidra will show every function that receives the same pointer type, giving you a list of all methods that operate on the class. This is the game-RE equivalent of recovering a class's method table.

6. Renaming, Annotating, and Exporting Findings

Reverse engineering is a long iterative process. The value of a Ghidra project compounds over time as you accumulate annotations. Consistent renaming practices are essential.

  • Rename functions (L key): Use a consistent naming convention. A common scheme is ClassName__MethodName (e.g., CPlayer__TakeDamage, CPlayer__Update). This makes the Symbol Tree navigable and searchable.
  • Add comments (semicolon key): Add end-of-line comments explaining non-obvious behavior. Pre-plate (function header) comments via right-click → Set Function Comment explain what the function does at a high level.
  • Bookmarks: Use Window → Bookmarks to mark important addresses. Categories like "PlayerCode", "Rendering", "NetworkManager" help navigate a large project.
  • Exporting offsets to code: Once you have identified key offsets, export them to a C++ header file for use in your research tool:
// offsets.h — Generated from Ghidra analysis of game v1.42.0
// Binary hash (SHA256): a1b2c3d4...
#pragma once
#include <cstdint>

// CPlayer offsets (relative to CPlayer* this pointer)
namespace Offsets {
  namespace CPlayer {
    constexpr uintptr_t isAlive       = 0x18;   // int32
    constexpr uintptr_t health        = 0x3C;   // float
    constexpr uintptr_t maxHealth     = 0x40;   // float
    constexpr uintptr_t positionX     = 0x44;   // float
    constexpr uintptr_t positionY     = 0x48;   // float
    constexpr uintptr_t positionZ     = 0x4C;   // float
    constexpr uintptr_t velocityX     = 0x8C;   // float
    constexpr uintptr_t velocityY     = 0x94;   // float
    constexpr uintptr_t teamId        = 0xB0;   // int32
    constexpr uintptr_t pWeaponSlot   = 0x100;  // CWeapon*
  }

  // Static offsets from module base (game.exe)
  namespace Static {
    constexpr uintptr_t pLocalPlayer  = 0x01A2B3C0; // CPlayer**
    constexpr uintptr_t pEntityList   = 0x01A2C000; // CEntityList*
  }
}

Save your Ghidra project regularly (File → Save Project). Projects can be exported as Ghidra Archive files (.gar) and shared with collaborators — the entire annotated analysis travels with the archive, minus the original binary.

Note:Offsets change with every game patch. Version your offsets.h file and tag it with the game version and binary hash so you know exactly which build the offsets are valid for. A single incorrect offset will produce silent data corruption in your research tool.
